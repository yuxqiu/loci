# 21 — Error handling in mature Rust CLIs and toolchains

Status: research, 2026-11-03. Background for a possible refactor of how loci builds,
names and documents command errors. Builds on D111/D112 (one error type, `Refusal`),
D222 (typed lint codes) and D194 (why no test reads `docs/`); cited, not repeated.

Question: how do mature Rust CLI tools and toolchains define, name, enrich, document
and map errors to exit statuses? What should loci take from them, given that its errors
are read by agents from a JSON envelope, that plugins in any language emit the same
envelope, and that no Rust caller branches on a refusal?

What loci has today (working tree at 8f6eeb2, 2026-11-03):

- **One refusal type.** `envelope::Refusal { exit: Exit, error: CmdError { code:
  String, message: String } }` (`crates/loci-core/src/envelope.rs` lines 233–275).
  `Refusal::refused(code, msg)` gives exit 1 and `Refusal::internal(code, msg)` exit 3.
  `Refusal::io(e)` and `Refusal::git(e)` are `internal("io" | "git", e.to_string())`.
  `Exit` is `Ok = 0`, `Refused = 1`, `Internal = 3`, and clap keeps 2 (lines 215–222).
  Every command returns `Result<Report, Refusal>` (D111).
- **Refusal codes are string literals at the call sites.** 63 `refused("…")` and 6
  `internal("…")` calls give 49 distinct codes. Two more sites compute the code:
  `PathProblem::refusal` (`path.rs` line 341) uses a lint `Code`, and `relink.rs` line
  196 takes a parameter. `Refusal` appears in 31 files. 32 sites call
  `map_err(Refusal::io)` or `Refusal::git`. Of these, 2 add the path by hand
  (`bench.rs` line 89, `init.rs` line 91); the rest do not. For example, `export.rs` lines 77–81 and `vault.rs` lines 142–143
  write files and report only the OS message, such as "Permission denied (os error
  13)".
- **Every code has one exit class.** No code string appears with both `refused` and
  `internal`, so the exit could be a property of the code (checked by script over
  `crates/`).
- **Lint codes are typed.** `lint::Code` is generated by `codes!`, which writes each
  variant and its string once and round-trips them (`lint/code.rs` lines 1–94). The
  rule table, editions and `--only` use it (D222). Plugin codes stay strings and must
  carry the `<plugin>.` prefix (`plugin.rs` lines 165–167).
- **Codes are documented in prose.** The spec gives lint codes a table (m0 §7.3) and
  each refusal code in the text of its command (m0 §8, §9). A script run for this note
  found every refusal code from `crates/` in `docs/specs/*.md`, apart from the test code
  `a.b`. Nothing keeps it that way: no test reads `docs/`, because the Nix source is
  `Cargo.toml`, `Cargo.lock`, `rustfmt.toml` and `crates` (`flake.nix` line 31; D194
  gives the same reason for not checking `--only`).
- **The envelope's `error` has no `hint`,** although a `Diagnostic` has one (m0 §8).

Conventions as in research 12 to 20: `[unverified]` means I did not confirm the claim
in a primary source, `[design inference]` is my own extrapolation, and `[gap]` means I
looked and found nothing. Source files were read at the commits listed under Sources,
and line numbers refer to those commits. Examples are neutral (`a.md`, `out/x.html`).

## TL;DR

| Project | Error value | Codes: where, checked how | Context | Exit statuses |
|---|---|---|---|---|
| rustc | `Diag` builder, must be emitted or cancelled (panics on drop) | `E0308`: a macro list in `rustc_error_codes`; `include_str!` of `EXXXX.md` for each one, so a missing explanation fails the build; **tidy** checks docs, doctests, UI tests and that each code is emitted or marked "no longer emitted", in both directions | spans, labels, notes, suggestions | 0, 1; a crash (ICE) prints a bug-report URL |
| cargo | `anyhow::Error` (`CargoResult`); `CliError { error, exit_code }` at the top | no codes | `with_context` naming the path (`cargo-util::paths`); printed as "Caused by:"; marker wrappers `VerboseError`, `InternalError`, `AlreadyPrintedError` | 0, or 101 for any failure (`From<anyhow::Error>` = 101) |
| cargo-util-schemas | a public opaque struct over a private `#[non_exhaustive]` thiserror `ErrorKind` | none | fields in the message | (library) |
| ripgrep / ignore | `ignore::Error` enum: `Partial(Vec)`, `WithPath`, `WithLineNumber`, `WithDepth`, … | none | the path is a variant that wraps the inner error | 0 match, 1 no match, 2 any error, **even with matches**; broken pipe is 0 |
| fd | `anyhow` at the top; walker errors printed and skipped | none | the walker error carries its path | 0/1 (results or not), 1 error, 130 SIGINT |
| ruff | lint: `Violation` structs (`#[derive(ViolationMetadata)]`); tool failure: `anyhow` | `codes.rs` `#[map_codes]` match from (linter, code) to rule; the explanation **is** the rule's doc comment; `ruff rule <code>` and the website are generated from it; a unit test rejects a rule without docs; renamed codes go in `rule_redirects.rs` | "ruff failed" then one "Cause:" line per chain link | 0 clean, 1 lint errors, 2 ruff itself failed |
| uv | per-crate thiserror enums; `anyhow` in the CLI; `UvError::{User, Argument, Unexpected}` picks the exit | none | the full source chain as "cause:" lines; `Hinted` trait adds "hint:" lines; `fs-err` names paths | 0, 1 user, 2 argument or unexpected, or the child's code |
| gitoxide | **was** one thiserror enum per function or module; **now** (2026) one erased `gix_error::Error` with a recovery `Class` and metadata, keeping concrete types only where callers match | none | `or_raise(|| message(…))` frames and key-value metadata | (library) |
| jj | `CommandError { kind, error, hints }` with kind `User`, `Config`, `Cli`, `BrokenPipe` or `Internal`; 49 `From` impls map library errors to a kind | none | "Caused by:" chain, then hints | 0, 1 user or config, 2 CLI, 3 broken pipe, 255 internal |
| nushell / miette | `ShellError` enum deriving `miette::Diagnostic` | `#[diagnostic(code(nu::shell::…))]` on each variant; not unique (several variants share one) | labels on spans, `help`, `url`; `IoError` holds `path`, `additional_context` and the Rust caller location | (shell) |

Guidance in one line each. thiserror is for designing your own error type, anyhow for
when you don't care. snafu: put the same `io::Error` into different variants by
context. error-stack: change the context at each module boundary and attach data along
the way. The API guidelines (C-GOOD-ERR): implement `Error`, be `Send + Sync`, never
use `()`, and write lowercase messages without trailing punctuation. sled: keep errors
that must be handled out of the global enum. matklad: reporting and handling are
different jobs, and for reporting he uses a "diagnostics factory" of constructor
functions. BurntSushi: applications may box, libraries define a type. eros: typed or
untyped per signature, with a context chain.

**Recommendation (details at the end): option (a), plus `loci explain` later.** Keep
`Refusal` and the envelope. Put the refusal codes in one source registry, as `codes!`
does for lint codes, with each code's exit class and a one-line summary, so that call
sites name a typed code. Replace bare `Refusal::io` and `Refusal::git` with a context
extension that names the operation and the path. Add a tidy-style check, in both
directions, between the two code registries and the spec. Do not move to per-module
thiserror enums or to anyhow chains: neither helps a reader who sees only `code` and
`message`, and the closest precedent, gitoxide, has just moved away from per-function
enums.

## 1. rustc

**Mechanism.** A diagnostic is a `Diag<'a>`: a builder around a boxed `DiagInner`,
marked `#[must_use]` and `!Clone`. It must be consumed by `emit`, `cancel` or
`delay_as_bug`; dropping it unconsumed emits a bug and panics ("error was constructed
but not emitted") (`compiler/rustc_errors/src/diagnostic.rs` lines 340–371,
1282–1296). The `code` field is an `Option<ErrCode>` (line 194). `ErrCode` is a
newtype index whose `Display` prints `E{:04}` (`compiler/rustc_errors/src/codes.rs`
lines 12–24).

**Where codes and explanations live.** `compiler/rustc_error_codes/src/lib.rs` holds
one higher-order macro, `error_codes!`, that lists every code in use as a bare number
(`0308,` at line 179). Removed codes stay as comments, and its header says: "Do *not*
remove entries from this list. Instead, just add a note to the corresponding markdown
file" (lines 8–24). `rustc_errors/src/codes.rs` (lines 27–51) expands the list twice: it
defines a constant per code (`E0308`) and a `DIAGNOSTICS` table that pairs each code with
`include_str!("../../rustc_error_codes/src/error_codes/E{num}.md")`. **A code without an
explanation file therefore fails to compile.** The explanation is Markdown in the form
set by RFC 1567: a one-line summary, then "Erroneous code examples:" with
`compile_fail,E0308` doctests (`error_codes/E0308.md` lines 1–20). The dev guide says to
take the next free number, write the `.md` file and add the number to the macro
(`src/doc/rustc-dev-guide/src/diagnostics/error-codes.md` lines 31–60). It also notes
that a draft RFC (rust-lang/rfcs#3370) would replace RFC 1567's format.

**Explain.** `rustc --explain E0308` (or `0308`) looks the code up with
`try_find_description` and prints the Markdown, through a pager on a terminal
(`compiler/rustc_driver_impl/src/lib.rs` lines 427–466). After a failed build, the
`DiagCtxt` prints "For more information about this error, try `rustc --explain
E0308`." for the codes it emitted that have explanations (`rustc_errors/src/lib.rs`
lines 808–845). With `--error-format=json`, every diagnostic's `code` object carries
`explanation`, the full Markdown text (`rustc_errors/src/json.rs` lines 235–242, 326).
A machine reader thus gets the explanation inline.

**Keeping codes and docs in sync: tidy.** `src/tools/tidy/src/error_codes.rs` (lines
1–17 state the plan) runs four stages:

1. Extract the codes from the macro (line 82).
2. Check that each code has an explanation file with a doctest that fails with that
   code. Exemptions are explicit lists (lines 31–36, 127).
3. Check that each code has a UI test, `tests/ui/error-codes/EXXXX.rs`, and its
   `.stderr` (line 241).
4. Search `compiler/` with the regex `\bE\d{4}\b`, outside comments. A code used but not
   in the list is an error ("used in the compiler but not defined and documented"). A
   listed code that is never used is an error unless its explanation says "no longer
   emitted" (lines 303–360).

It also fails if a diff deletes an explanation file ("Error code explanations should
never be removed!", lines 60–80). The check runs in both directions, is driven by a
regex over the source tree, and is a separate tool, not a unit test.

**Exit statuses.** `EXIT_SUCCESS = 0` and `EXIT_FAILURE = 1` ("compilation failures and
invalid flags") (`rustc_driver_impl/src/lib.rs` lines 111–115). An internal compiler
error prints `DEFAULT_BUG_REPORT_URL` (lines 117–118). Its exit status is the Rust
panic default of 101 [unverified].

**For loci.** Three ideas carry over: a code list as a macro whose expansion forces
each code's documentation to exist, an explanation that a machine reader receives in
the JSON, and a check that scans both ways without being part of the build. A crate
cannot `include_str!` a file outside the Nix source (`docs/`), so loci would need its
explanation files in `crates/`, as rustc keeps them in `compiler/`.

## 2. cargo

**Mechanism.** `pub type CargoResult<T> = anyhow::Result<T>;` (`src/util/errors.rs`
line 11; cargo has moved `src/cargo/` to `src/`). At the CLI layer, `CliError { error:
Option<anyhow::Error>, exit_code: i32 }` (lines 308–338). `From<anyhow::Error>` sets
101, `From<clap::Error>` sets 0 or 1, and `From<std::io::Error>` sets 1 (lines
343–360). The documented statuses are only "`0`: Cargo succeeded" and "`101`: Cargo
failed to complete" (`doc/man/includes/section-exit-status.md`).

**Context.** cargo builds messages by layering `with_context`. Its fs helpers wrap
every std call so that the path is always named: `read` is "Equivalent to
`std::fs::read_to_string` with better error messages", and gives "failed to read
`{path}`" (`crates/cargo-util/src/paths.rs` lines 166–190; the same for write, create,
open and create directory). The printer walks `err.chain()`: the first link is printed
as `error:`, each later one under "Caused by:" (`src/lib.rs` lines 236–250). Three
marker wrappers change the display without adding text (`src/util/errors.rs` lines
136–245). `VerboseError` cuts the chain unless `--verbose`. `AlreadyPrintedError` stops
it. `InternalError` makes `display_error` add "this is an unexpected cargo internal
error" and a bug-report note (`src/lib.rs` lines 196–213). `ManifestError` adds the
manifest's path to the chain (`errors.rs` line 246).

**Structured errors in `cargo-util-schemas`.** The schema crate uses thiserror, and
hides the enum behind an opaque struct:
`pub struct NameValidationError(#[from] ErrorKind)` over a private `#[non_exhaustive]
enum ErrorKind { Empty, InvalidCharacter { ch, what, name, reason }, … }`
(`crates/cargo-util-schemas/src/restricted_names.rs` lines 5–35). The same shape is
used for `PartialVersionError`, `PackageIdSpecError` and `RustVersionError`. Callers
get a typed error with a good message that no one outside the crate can match on, so the
crate can add variants freely.

**No codes.** cargo's errors carry no stable identifiers [gap: I found none in
`errors.rs` or `lib.rs`].

**For loci.** Two ideas carry over. First, a path-naming wrapper at the I/O boundary,
written once (this is loci's `Refusal::io` gap). Second, marking a failure as a bug,
not an environment problem, so that the reader is told to report it.

## 3. ripgrep, the `ignore` crate, and fd

**ignore.** One public enum, `ignore::Error` (`crates/ignore/src/lib.rs` lines
68–120). `Partial(Vec<Error>)` is "a collection of 'soft' errors", used when an ignore
file partly loaded. Context is a wrapping variant: `WithPath { path, err }`,
`WithLineNumber { line, err }` and `WithDepth { depth, err }`. Then come the leaf
variants `Loop`, `Io`, `Glob { glob, err }`, `UnrecognizedFileType` and
`InvalidDefinition`. Predicates see through the wrappers (`is_partial`, `is_io`, lines
162–235). `Display` prints `"{path}: {err}"` and `"line {n}: {err}"` (lines 327–360),
so every walker error names its file. A `PartialErrorBuilder` collects the soft errors,
and loading still returns the matcher built from the good lines
(`crates/ignore/src/gitignore.rs` lines 109–115).

**ripgrep: keep going and report.** The `messages` module explains the policy:
"Aside from errors associated with invalid CLI arguments, ripgrep generally does not
abort when an error occurs … when an error message is emitted via `err_message`, then a
global flag is toggled" (`crates/core/messages.rs` lines 1–25). `err_message!` sets
`ERRORED` and prints (lines 82–87). A per-file search error is printed as `"{path}:
{err}"`, and the loop continues (`crates/core/main.rs` lines 128–133). At the end, the
exit is 0 on a match (unless an error occurred and `--quiet` is off), 2 if any error was
reported, and 1 otherwise (lines 94–100). A fatal error is printed with `{:#}` (anyhow's
one-line chain) and exits 2. A broken pipe anywhere in the chain exits 0, matching Unix
convention (lines 43–66). `--json` output has only `begin`, `end`, `match`, `context`
and `summary` messages (`crates/printer/src/json.rs` lines 135–142), so errors stay on
stderr even in JSON mode.

**fd.** `fd` uses anyhow for fatal errors (`"[fd error]: {:#}"`, exit 1) (`src/main.rs`
lines 68–81). Walker errors are `WorkerResult::Error(ignore::Error)`. They are printed
only with `--show-errors` and do not change the exit (`src/walk.rs` lines 225–229). A
partial ignore-file error is skipped silently, and a full one is printed as "Malformed
pattern in … ignore file" (lines 370–395). The exit codes are an enum: `Success` 0,
`HasResults(bool)` 0 or 1, `GeneralError` 1, `KilledBySigint` 130, after re-raising
SIGINT (`src/exit_codes.rs` lines 6–23). Error text is sanitized for terminal control
characters before printing (`src/error.rs`).

**For loci.** The path belongs in the error. ignore puts it in the type, ripgrep in the
message. loci already chose the opposite policy from ripgrep for unreadable files (D152:
refuse the vault), while lint keeps going, as ripgrep does. Neither choice needs to
change.

## 4. Astral: ruff and uv

### 4.1 ruff's rule-code registry

**Mechanism.** A rule is a struct that derives `ViolationMetadata` and implements
`Violation`. For example, `UnusedImport` carries `#[violation_metadata(stable_since =
"v0.0.18", category = Category::Suspicious)]`, and `fn message(&self) -> String` is
marked `#[derive_message_formats]`
(`crates/ruff_linter/src/rules/pyflakes/rules/unused_import.rs` lines 145–182).
`ViolationMetadata` provides `rule()`, `explain()`, `status()`, `category()`, `file()`
and `line()` (`crates/ruff_linter/src/violation.rs` lines 31–50).

**Where codes live.** One function, `code_to_rule(linter, code)`, is annotated
`#[ruff_macros::map_codes]`. Its body is a single match: `(Pyflakes, "401") =>
rules::pyflakes::rules::UnusedImport,` (`crates/ruff_linter/src/codes.rs` lines 237–317).
The macro generates the `Rule` enum and the selector prefixes (`C`, `C4`, `C41`) (lines
1–7). The code is `NoqaCode(prefix, suffix)` (line 20). Renamed or regrouped codes are
kept as redirects (`("SIM111", "SIM110")`, `("R", "RET")`)
(`crates/ruff_linter/src/rule_redirects.rs` lines 1–25).

**Where explanations live, and how they stay in sync.** The explanation is the struct's
doc comment, with `## What it does`, `## Why is this bad?` and `## Example` sections
(`unused_import.rs` lines 27–143). The derive macro collects the `#[doc]` attributes into
`fn explain() -> &'static str` (`crates/ruff_macros/src/violation_metadata.rs` lines
9–52, 62–75). Everything downstream is generated:

- `ruff rule <code>` builds an `Explanation { name, code, linter, summary,
  message_formats, fix, explanation, preview, status, category, source_location }` and
  prints it as text or JSON (`crates/ruff/src/commands/rule.rs` lines 15–58).
- `cargo dev generate-docs` writes `docs/rules/<name>.md` for every rule
  (`crates/ruff_dev/src/generate_docs.rs` lines 28–75, 145–156). These files are not
  committed: no `docs/rules/` exists in the tree, and CI generates them before building
  the site (`.github/workflows/ci.yaml` lines 1247–1252).
- A unit test fails on any rule whose explanation is empty ("Rule {} is missing
  documentation") (`crates/ruff_linter/src/registry.rs` lines 484–493), and another
  enforces the naming convention.
- Other generated files (CLI help, JSON schema) have a `--mode check` that errors when
  the file is out of date, run as tests (`crates/ruff_dev/src/generate_all.rs` lines
  16–33; `generate_cli_help.rs` lines 144–146).

The contributor steps are: write the struct and its doc comment, register it in
`codes.rs`, add fixture tests, and regenerate (`CONTRIBUTING.md` lines 199–239).

**I/O as a diagnostic.** A file that cannot be read becomes a diagnostic with a code
(`(Pycodestyle, "E902") => IOError`, `codes.rs` line 303), so linting continues.

**Exit statuses and tool failure.** `ExitStatus::Success` 0 ("no linting errors"),
`Failure` 1 ("there were linting errors"), `Error` 2 ("Linting failed")
(`crates/ruff/src/lib.rs` lines 38–55). A tool failure is an `anyhow::Error`. It prints
"ruff failed", then one `Cause:` line per link of the chain. The comment explains why:
"with io errors when resolving the configuration it is help to chain errors". A broken
pipe exits 0, with a link to ripgrep's code (`crates/ruff/src/main.rs` lines 50–78).
Rendering uses ruff's own fork of annotate-snippets (`Cargo.toml` line 18).

### 4.2 uv

**Mechanism.** Errors are per-crate thiserror enums. For example,
`uv_distribution`'s `error.rs` has 54 `#[error]` attributes. Some wrap other crates with
`#[from]`, and others are specific, such as `CacheRead(#[source] std::io::Error)` ("Failed
to read from the distribution cache") (`crates/uv-distribution/src/error.rs` lines
39–75). The files in `uv-client` and `uv-resolver` have 32 and 18. The CLI uses anyhow. uv does not use
miette or annotate-snippets: neither is in the workspace dependencies (`Cargo.toml`),
and miette reaches `Cargo.lock` only through the `axoupdater` self-updater.

**Classification picks the exit.** `UvError::{User(anyhow::Error),
Argument(anyhow::Error), Unexpected(anyhow::Error)}` ("A command error propagated to the
entrypoint for exit-status selection"). `map_user` adds context to user errors only
(`crates/uv-command-support/src/lib.rs` lines 35–76). The entry point downcasts to
`UvError`. An error that is not a `UvError` is `Unexpected`, and its debug chain and
backtrace go to the trace log (`crates/uv/src/lib.rs` lines 3141–3176). The statuses
are `Success` 0, `Failure` 1 ("caused by user input"), `Error` 2 ("unexpected failure")
and `External(code)` (`uv-command-support/src/lib.rs` lines 21–33, 78–87).

**Context and hints.** `write_error_chain_with_options` prints `error: <top>`, then
`cause: <link>` for each source, wrapped to the terminal, then `hint: …` lines
(`crates/uv-errors/src/lib.rs` lines 346–403). Hints come from a `Hinted` trait that an
error type implements: "Implement this on error types that want to surface contextual
suggestions … Hints are rendered after the error output, each prefixed with `hint:`"
(lines 12–23). An example is `ExternallyInstalledError` (`crates/uv/src/lib.rs` lines
109–129). The style guide fixes the form: a blank line, then `hint: <content>`
(`STYLE.md` lines 132–136). File paths come from `fs-err` (`Cargo.toml` line 182), a
drop-in `std::fs` whose errors name the path [the crate's behaviour: unverified, not
read].

**No codes.** uv's errors have no stable identifiers [gap].

**For loci.** From ruff, three ideas: the explanation lives next to the code that emits
it, docs are generated so they cannot drift, and a unit test proves every code is
documented. From uv: the exit class is chosen by a small kind enum, separate from the
message, and hints are a field, not part of the message.

## 5. gitoxide (gix)

**The old philosophy.** In 2022, the maintainer answered a request for one crate-wide
error type: "This is intentional and I consider an aggregate type (using `thiserror`
anyway) a mistake … it's terrible to not know which of the many variants actually
apply." Per-method errors let a caller "match on all variants without default to get a
compile error if something is added" (issue #670, comments 1363707217 and 1364500417).
`DEVELOPMENT.md` then said: "provide an error chain and make it easy to understand what
went wrong. We `thiserror` generally" (at tag `gix-v0.66.0`, lines 16–18). A typical
example was `gix::open::Error { Config, NotARepository { source, path }, Io,
UnsafeGitDir { path }, EnvironmentAccessDenied }` (`gix/src/open/mod.rs` at
`gix-v0.66.0`, lines 45–59).

**The 2026 reversal.** Issue #2351, "Reorganise Error-Handling around `Exn`" (January
2026), counted the `thiserror` derives per crate: 138 in `gix`, 23 in `gix-pack`, and so
on. It planned to replace them all. PR #2716 (closed without merging; checked with the
GitHub API, 2026-11-03) proposed removing `thiserror` from 67 of 68 crates in three
tiers:

- plumbing crates keep concrete enums with hand-written impls;
- 14 crates adopt `gix-error` directly;
- the `gix` boundary erases to `pub type Error = gix_error::Error;` "where callers don't
  need to match variants" (101 types).

That PR also reported that its branch "adds roughly 6,000 lines net", mostly from
hand-writing what thiserror had generated. PR #2847 (merged 2026-09-24) completed the migration: zero
first-party thiserror derives remain, and 31 custom types are kept because "some
remaining types support recovery or downcasting".

**The new mechanism.** `gix_error` organises errors as a tree of frames, built on the
`exn` crate ("A context-aware concrete Error type", `fast/exn` README). Each error
carries an optional recovery `Class`: `Cancelled`, `Corruption`, `ResourceExhaustion`,
`Validation`, `Unsupported`, `Unauthenticated`, `PermissionDenied`, `Conflict`,
`NotFound` or `Retryable`. Its documentation says: "Classes describe different
remedies, not just different wording … Leave errors unclassified when the remedy is
unknown" (`gix-error/src/lib.rs` lines 1–36). Context is added with
`or_raise(|| message("Could not open repository"))`. Data goes in typed metadata, such as
`.with("path", Path::new("HEAD"))`, and "Callers should add context using information
they already possess and document its keys on the function that returns it" (lines
37–60, 120–140). `gix::open` now returns `gix::Result<Self>` (`gix/src/open/
repository.rs` lines 58–81; `gix/src/lib.rs` lines 44–60, 179).

**Codes and exit statuses.** Neither: gix is a library, and its CLI (`gitoxide`) uses
anyhow.

**For loci.** This is the strongest evidence against option (b). The project best known
for fine-grained thiserror enums decided they cost more than they gave wherever callers
do not match on variants. What it kept is what loci already has: a small
classification, distinct from the message, that chooses the remedy (loci's
`Exit::Refused` against `Exit::Internal`), plus context that names the inputs.

## 6. jj (jujutsu)

**Mechanism.** `CommandError { kind: CommandErrorKind, error: Arc<dyn Error + Send +
Sync>, hints: Vec<ErrorHint> }`. The kind is `User`, `Config`, `Cli` ("Invalid command
line. The inner error type may be `clap::Error`"), `BrokenPipe` or `Internal`
(`cli/src/command_error.rs` lines 95–110). The constructors are free functions:
`user_error`, `config_error`, `cli_error`, `internal_error` and their `_with_message`
forms, which wrap a source under a user-visible message (lines 172–229). `.hinted(…)`
adds a hint (line 133). An `ErrorHint` is `PlainText` or `Formatted` (lines 165–169).

**Where messages live.** The file has 49 `impl From<LibError> for CommandError`, and each
one decides the kind and the message. `BackendError::Unsupported` is a user error, and
any other `BackendError` is internal, "Unexpected error from backend" (lines 474–481).
`io::Error` is `BrokenPipe` or `User` (lines 393–401). Stale working copies get hints
naming the recovery command (lines 300–323). jj has no error codes.

**Exit statuses.** `User` and `Config` give 1, and `Config` also adds a hint pointing at
the config docs. `Cli` gives 2 (clap's own rendering when the error is a clap error),
`BrokenPipe` 3, and `Internal` 255 ("Internal error: "). The sources print as "Caused
by:", then the hints (lines 1184–1260).

**For loci.** jj keeps the mapping from library error to kind in one file at the CLI
boundary, so the library crate needs no CLI types. loci needs no such layer: its
library already returns `Refusal`, and only one binary family consumes it. The useful
idea is that hints are separate from the message (see uv).

## 7. nushell and miette

**miette.** The `Diagnostic` trait extends `std::error::Error` with these methods:
`code()`, `severity()`, `help()`, `url()`, `source_code()`, `labels()`, `related()` and
`diagnostic_source()` (`src/protocol.rs` lines 15–85). About `code()`, the trait says:
"Unique diagnostic code that can be used to look up more information … Ideally also
globally unique, and documented in the toplevel crate's documentation … Rust path format
(`foo::bar::baz`) is recommended, but more classic codes like `E0123` … will work just
fine" (lines 21–26). The derive takes `#[diagnostic(code(my_app::my_error),
url(docsrs))]`, where `url(docsrs)` links to the type's page on docs.rs. The code thus
leads to documentation that sits next to the type (`README.md` lines 360–392). There is
a `JSONReportHandler` for machine-readable output (`src/handlers/json.rs` lines 7–11).

**nushell.** `ShellError` is one large enum deriving `Error` and `Diagnostic`. Each
variant has a message template, `#[diagnostic(code(nu::shell::…))]`, `#[label]` fields
on spans and an optional `#[help]` (`crates/nu-protocol/src/errors/shell_error/mod.rs`
lines 24–60; 68 `code(...)` attributes in that file). The codes are categories, not
identities: `nu::shell::type_mismatch`, `nu::parser::variable_not_valid` and
`nu::parser::unexpected_keyword` each name three variants, and nothing checks
uniqueness (counted over `crates/nu-protocol/src/errors/`). The I/O error is a struct
that answers loci's `Refusal::io` problem directly. It has `kind`, `span`, and
`path: Option<PathBuf>`, because "operating system error messages often don't include
the specific path". It also has `additional_context`, set "only … if it adds meaningful
context", and `location`, the Rust caller location via `#[track_caller]` for internal
errors (`shell_error/io.rs` lines 97–135, 312–371).

**For loci.** loci already uses miette's naming scheme: namespaced codes, with the
`<plugin>.` prefix as the namespace (`plugin.rs` lines 165–167). nushell shows what
happens when codes are attributes without a registry or a uniqueness check: they drift
into categories.

## 9. Error crates and guidance

- **thiserror vs anyhow.** The two READMEs divide the work: "Use thiserror if you care
  about designing your own dedicated error type(s) so that the caller receives exactly
  the information that you choose … Use Anyhow if you don't care what error type your
  functions return" (thiserror `README.md` lines 211–217; anyhow `README.md` lines
  155–160). thiserror "deliberately does not appear in your public API": it generates
  what a hand-written impl would (thiserror lines 46–49). anyhow's context is
  `.context("Failed to …")` and `.with_context(|| format!("Failed to read instrs from
  {}", path))` (anyhow lines 41–55).
- **snafu.** "Categorize underlying errors by their context: It should be easy to bin
  one underlying error type (such as `io::Error`) into multiple domain-specific errors
  while optionally adding contextual information". Also "Each module should have one
  (or more!) error types" (`src/guide/philosophy.md` lines 7–23). The README example is
  `fs::read_to_string(path).context(ReadConfigurationSnafu { path })?` beside
  `fs::write(&path, …).context(WriteResultSnafu { path })?` (`README.md` lines 29–31).
  This is the same operation-plus-path context that loci's `Refusal::io` lacks.
- **error-stack.** A `Report<C>` holds a stack of contexts. `change_context(NewC)` swaps
  the type at a module boundary, and `attach(…)` adds data without changing the type. The
  rendered report is a tree with source locations (`libs/error-stack/README.md`, the
  `parse_experiment` example).
- **eros.** `eros::Result<T>` (untyped) or `eros::Result<T, (io::Error, ParseError)>`
  (a typed union), with `.context()` chains. The README's philosophy: "Error types only
  matter when the caller cares about the type, otherwise this just hinders ergonomics"
  (`README.md` lines 1–25). It describes two ways to place context, with their costs:
  "Attach Context at the Function" with `#[context("…", param)]`, which avoids gaps but
  may repeat; or "Attach Context Where Information Would Be Lost", which is lean but
  "it is also easy to get lazy and skip attaching context altogether" (lines 601–665). Its
  JSON report (`root`, `sources`, `contexts`) is "not covered by SemVer guarantees"
  (`docs/json.md` lines 1–30).
- **Rust API Guidelines, C-GOOD-ERR.** An error type implements `std::error::Error`,
  `Send` and `Sync` (`'static` for `downcast_ref`). Never use `()`. "Define a meaningful
  error type specific to your crate or to the individual function". "The error message
  given by the `Display` representation … should be lowercase without trailing
  punctuation, and typically concise" (`src/interoperability.md` lines 190–262).
  `Refusal` already implements `Error` (D233).
- **sled, "Error Handling in a Correctness-Critical Rust Project"** (Tyler Neely,
  2020-04-08). The post cites a study finding that "almost all (92%) of the catastrophic
  system failures" came from bad handling of non-fatal errors. Its remedy is to "make
  the global Error enum specifically only hold errors that should cause the overall
  system to halt … Keep errors which relate to separate concerns in totally separate
  error types". For example, `compare_and_swap` returns `Result<Result<(),
  CompareAndSwapError>, sled::Error>`. "Do not implement conversions from local concerns
  into global enums." loci's `Refusal` is exactly the "halt and report" type. Its local
  concerns are already separate types: `PathProblem`, `LinkError`, `Dangling` (D222,
  D242).
- **matklad.** "Study of std::io::Error" (2020): ask "how the error will be used?".
  Either it is "handled programmatically", so its structure must be exposed, or it is
  "propagated and displayed to the user", so it can be encapsulated. A "kitchen-sink
  enum" of dependency errors is an anti-pattern. `io::Error` pairs a public fieldless
  `#[non_exhaustive]` `ErrorKind` with an opaque representation. "Error Codes for
  Control Flow" (2025-11-06): "Displaying an error message to the user is a different
  aspect of error handling than branching based on a specific error condition … a lean
  handling type might be just an enumeration of all different code-paths — an error
  code". "Diagnostics Factory" (2026-02-16): "avoid thinking about error payloads … provide
  a set of functions for constructing errors". There is then "one central place that
  enumerates all possible errors", grep-able call sites, and a natural place to turn
  offsets into line numbers.
- **BurntSushi, "Error Handling in Rust"** (2015). For a program, "define your own error
  types with appropriate `From` and `Error` impls". For a library, "define your own error
  type", exposing its representation (like `ErrorKind`) or not (like `ParseIntError`),
  and "provide some information about the error beyond just its String representation"
  (sections "Advice for library writers" and "The short story").

**What they agree on, applied to loci.** Errors serve two purposes: handling by code and
reporting to a reader. loci's refusals are only reported, and the reader is an agent. For
reporting, the guidance favours a stable identifier for branching (matklad's error code,
`io::ErrorKind`), messages that carry context (snafu, cargo, nushell), and one central
place that constructs them (matklad's factory, rustc's macro, ruff's `codes.rs`). None of
them asks for a sum type with payloads when no code matches on it (gitoxide, eros, sled,
matklad).

## 11. Options for loci

Site counts are from `crates/` at 8f6eeb2. Option (b) is shown at its smallest useful
size.

### (a) Keep `Refusal`; add a refusal-code registry, a context extension, and a check in both directions

- **What.**
  - A `refusals!` table in `loci-core` written like `codes!`. Each row gives a variant,
    the code string, its exit class and a one-line summary:
    `MvExists => "mv.exists", Refused, "the destination already exists"`.
  - `Refusal::new(RefusalCode::MvExists, msg)` takes the exit from the code, so a code
    can no longer exit 1 at one site and 3 at another (today's data already holds this
    by convention).
  - `CmdError.code` stays a `String` in the envelope, so plugin refusals still
    deserialize. Only core's construction is typed.
  - An extension trait replaces bare `Refusal::io` and `Refusal::git`:
    `fs::write(&out, text).io("writing", &out)?` gives `io`: "writing `out/x.html`:
    Permission denied (os error 13)". The git module's `Result<_, String>` messages
    already name the git command (`git.rs` lines 240–260), so `git` sites need only the
    operation.
  - A tidy-style check, after rustc's, reads `lint::Code`, the refusal table and the
    backticked codes in `docs/specs/*.md`. It fails when a source code is missing from
    the spec, or when a spec code that looks like a core code (`<area>.<name>`, not a
    plugin prefix) is in neither table. It runs in the dev shell or CI, outside the Nix
    build (D194). The alternative is to add `docs/specs` to the Nix fileset (`flake.nix`
    line 31), so that an ordinary `cargo test` can read it.
- **Cost.** 1 new module (about 80 lines with the table, similar to `lint/code.rs`'s
  107). About 69 literal sites and 2 computed ones change mechanically, by codemod. 32
  io/git sites get an operation and path. The check is 1 script or test. The touched
  files are about 31. No JSON output changes, except that io messages gain the
  operation and the path.
- **Fit.** High. Agents and plugins see the same envelope. The registry is a single list
  that a person or an agent can read, and the check ends silent drift between spec and
  source. It follows loci's own precedent of writing a thing once (`codes!`, D222; D191
  derived `core_commands()` from clap instead of syncing it by a test).
- **Risks.**
  - The spec check parses prose. A false positive needs an allow-list, like rustc's
    exemption lists.
  - D194 records that the user rejected a registry for update tags. This is a different
    registry, of codes that already exist, but it should be proposed as such.
  - The summary column partly duplicates the spec's prose.

### (b) Per-module thiserror enums, converted to `Refusal` at the CLI boundary

- **What.** `mv::Error`, `new::Error`, `vault::OpenError`, `relink::Error` and so on.
  Each variant has a `#[error("…")]` message and a code, through a trait or attribute,
  plus `impl From<mv::Error> for Refusal`.
- **Cost.** High. About 15 modules get an enum, about 50 variants are defined, the
  `From` impls or a derive are written, and every function signature that returns
  `Refusal` today (56 functions in 30 files) changes. gitoxide's experience in the other
  direction was estimated in the thousands of lines (the unmerged PR #2716, "+6,000 net").
- **Fit.** Low. No Rust caller matches on a refusal. sled and matklad say typed
  variants pay off only where code branches, and loci already has typed values there
  (`PathProblem`, `LinkError`). The agent sees the same `code` and `message` either way.
  Variant names would also be a second name for every code, unless a macro derives one
  from the other, which brings back (a)'s table.
- **Risks.**
  - A second source of truth (the variant and its code).
  - Churn in signatures.
  - The temptation to add `#[from] io::Error`, which brings back the context-free `io`
    message that this refactor wants to remove (snafu's warning).

### (c) anyhow-style context chains

- **What.** Internal functions return `anyhow::Result` (or `Report`), and context is
  added at each layer. The CLI finds the code by downcasting to a `Refusal`, or defaults
  to `io` or `internal`, as uv does with `UvError`. The envelope's `message` is the chain
  joined on one line (`{:#}`, as ripgrep and fd print it).
- **Cost.** Medium. A dependency, about 100 changed sites, and a rule for which layer adds
  context.
- **Fit.** Medium to low. The chain helps a human debug a deep failure, but loci's call
  depth from command to I/O is shallow (command, then core plan, then fs). A code that
  falls through to a default is a silent fallback, which loci's rules forbid. Two
  pieces of context (operation and path) cover the observed gap.
- **Risks.**
  - Codes become optional. A forgotten downcast or wrap reports `io` where a specific
    code was meant.
  - Messages grow repeated context ("reading x: reading x: …"; eros's warning).

### (d) A generated code registry with `loci explain <code>`

- **What.** Each core code (lint and refusal) gets an explanation. In the rustc style,
  this is one Markdown file per code in `crates/loci-core/explain/` loaded with
  `include_str!` by the registry macro. In the ruff style, it is a doc string in the
  table. `loci explain link.dangling [--json]` prints it. For a plugin code, `loci
  explain learn.x` calls a new optional `explain` hook, or else answers "documented by
  plugin `learn`". The spec's code tables could then be generated from the registry and
  checked with `--check`, ruff's model.
- **Cost.** About 85 explanations (34 lint codes, about 50 refusal codes), plus 1 command,
  1 optional plugin hook in the protocol (m0 §8 and the plugin spec), and a generator
  for the spec tables, or keeping (a)'s check. The registry from (a) is a precondition.
- **Fit.** Medium to high for lint codes: an agent that meets `fm.id-duplicate` can learn
  why the rule exists and how to fix it, without the spec. Lower for refusals, whose
  messages already say what to do (`path.outside`, `mv.exists`). rustc's choice to put the
  explanation inside the JSON suggests an `explanation` field instead of a command, but
  that adds bulk to every envelope.
- **Risks.**
  - About 85 texts to maintain, which can drift from the spec unless one generates the
    other.
  - The new plugin hook is a protocol change.
  - Explanations written before the rules settle will need rewriting.

### Combinations

- **(a) + (d), staged.** Do (a) now. Add (d) for lint codes later, once the rule set is
  stable, reusing the registry. This is the recommendation.
- **(a) + the context half of (c).** This is already inside (a): an extension trait
  gives the operation-plus-path context without anyhow.
- **(b) + (a).** Only for a module where a caller starts to branch on the reason. That
  would be a local typed error, as `PathProblem` already is, not a general move.

**Ranked:** 1. (a); 2. (a) + (d) for lint codes; 3. (d) alone (it needs (a)'s registry
anyway); 4. (c); 5. (b).

## Recommendation

**Do (a), and plan (d) for lint codes after it.** The reasons follow.

1. **The reader sees only `code`, exit and `message`.** Typed enums (b) and context
   chains (c) improve what Rust code can inspect. In loci, nothing inspects a refusal
   after it is built. gitoxide reached the same conclusion for its own boundary in 2026
   (the unmerged PR #2716 and the merged #2847): erase where callers do not match, and keep concrete types where
   they do. loci already keeps those (`PathProblem`, `LinkError`, `Dangling`).
2. **The weaknesses that exist are drift and missing context, and (a) fixes both.**
   Today the codes agree with the spec only by discipline, and 32 io/git sites lose the
   path. rustc (macro list plus tidy), ruff (one match plus generated docs) and loci's
   own `codes!` all solve drift with one list in source. cargo, snafu, ignore and
   nushell all solve missing context by naming the operation and the path at the I/O
   boundary.
3. **Binding the exit to the code** removes a free choice at each call site, using what
   uv and jj do with a kind enum. loci's data already has one exit per code.
4. **(d) is worth it for lint codes, not now.** rustc and ruff show the value of an
   explanation that a machine can fetch. But loci's rules are still changing (research
   19), and an agent today gets the rule from the spec-derived skills and hints. With
   (a)'s registry in place, (d) is an addition, not a refactor.

Small additions to consider with (a), each a separate decision:

- **`hint` on `CmdError`,** as uv and jj keep hints separate. This is an additive
  envelope field: today, advice is inside the message.
- **A separate code for bugs.** Today `lint.fix` (exit 3) also covers "should not
  happen" failures (`fix.rs` line 211). cargo's `InternalError` adds "please report"
  advice. jj gives internal errors their own exit (255).
