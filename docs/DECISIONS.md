# Decisions

Append-only log of decisions about loci, newest last, with their reasons. `DESIGN.md` and `docs/specs/` describe the current system; evidence is in `research/`. A later entry supersedes an earlier one where they conflict.

## 2026-10-30
- D1. Plain markdown + git is the source of truth; every index/embedding/graph is a rebuildable cache.
- D2. Concepts are canonical. Reading paths, timelines, folders are views; papers/clippings are immutable sources; research logs are kept as an own, chronological journal.
- D3. No concept/technique distinction. A frontmatter field exists only if a tool or procedure reads it. Results and questions are not knowledge; their type is their location.
- D4. Tooling: one Rust binary `loci` (Nix-packaged) enforces invariants; judgement lives in agent skills. CLI first, MCP wrapper later only if needed.
- D5. (Superseded by D73: no authorship tracking.) Provenance via git: agent commits under its own author on review branches; merge to `main` = user review = promotion gate. Concepts may cite only sources, code anchors or commits, never other concepts, as evidence.
- D6. (Mechanism amended by D41/D57.) Processed inbox drafts and migrated notes are deleted from the tree in the same commit that integrates them; git history is the archive. An `authored` event in `learner/events/YYYY.jsonl` keeps the authorship signal.
- D7. (Superseded by D27.) Learner states are unseen / encountered / known; only graded recall makes a concept known. Implicit signals (notes, searches, browsing) are exposure only.
- D8. Phone search: point hister at the vault (no new code). Agent retrieval is `loci` (see D13).
- D9. The agent works on demand (terminal session or user-started inbox run); nothing runs on a schedule. No nvim changes; directives are `<!-- loci: ... -->` comments.
- D10. (Superseded by D69: no reading note.) Annotated PDFs: user exports from sioyek; paper stays as a source, annotations become the reading note.
- D11. Review cards live in the system (FSRS); no Anki export.
- D12. `loci export` produces self-contained md/html/pdf from a view or concept (inline listed links, dedupe, glossary for the rest).
- D13. No persistent search index at first: flat carrel-style digests + in-memory BM25 `loci find` + grep. A persistent hybrid index is added only when `loci bench` shows misses it fixes.
- D14. The system is named **loci** (CLI `loci`); content lives in a separate vault repo.
- D15. No free-form tags. Aliases for retrieval, hub-concept links for themes, views for collections; `loci lint` rejects `tags:`.
- D16. `loci bench` (tool level + agent level + procedure goldens) is the gate for retrieval/structure changes and for simplifying skills as models improve.
- D17. Agent-agnostic: rules in AGENTS.md, skills in .agents/skills; no per-host adapter files; session state via `loci status`, not host hooks.
- D18. Existing areas need not be preserved; the agent may refactor the area tree.
- D19. Images move with the concept they illustrate; their content (slides, diagrams) is extracted into concept text where it carries knowledge.
- D20. The agent builds and maintains STYLE.md from the user's writing; the user adds their own rules to it.
- D21. Review is plain `git diff`.
- D22. Card review happens in the terminal (`loci review`). No `loci serve` for now (idea kept for later).
- D23. Code knowledge lives only in the vault; deferred until migration is done.
- D24. Browsing history is not a learner signal for now.
- D25. Migration cost is estimated after the pilot.
- D26. The agent may add frontmatter and concept links to research logs.
- D27. (Estimate model refined by D58.) Knowledge estimate is continuous and decays: per-concept FSRS-style stability/retrievability, updated by graded recall (full weight), rereading (small, capped), authoring (initial prior); searches logged only. Procedures set their own thresholds; no "known" label. Supersedes D7.
- D28. Note size: one note per concept with sections; an idea earns its own note when it has its own definition and >=2 linking notes/views; soft lint budgets (research/03).
- D29. Relations: `relations.toml` registry enforced by `loci lint`; start with `prereqs` only (direct edges stored, closure computed); new types need a reading procedure, a definition, a 20-edge reviewed pilot and a DECISIONS entry; complex relations become notes (research/04).
- D30. (Vault-specific; moved to the private migration notes.)
- D31. (Superseded: no exposure events in v1, D69.) "Reopen" events are counted only for access through `loci` (find, export, review); no editor or browser tracking.
- D32. (Configurable kinds superseded by D70; configurable paths by D72.) Two kinds of thing: concepts and records. Record kinds (source, journal, draft) are declared in `loci.toml` with path, author, keep-after-extraction. No special cases for languages or personal notes.
- D33. No FOCUS.md. Recency context comes from `loci recent`.
- D34. Review cards live as a `## Cards` section in their concept note (block ids); scheduling state is recomputed from `learner/events/YYYY.jsonl`.
- D35. Learner events are sharded yearly (`learner/events/YYYY.jsonl`), merged with git's union driver, and replayed through a rebuildable snapshot cache in `.loci/`.
- D36. The journal is split into streams (`journal/research/`, `journal/life/`); a stream is just a folder.
- D37. (Classification superseded by D43; reading note by D69; `confused` deferred, D42.) The inbox is a queue, not a record kind; items are classified on processing. Annotated PDFs become sources with a user reading note (`note.md`) and `annotated`/`confused` learner events.
- D38. Learner events and estimation follow docs/specs/learner-events.md (observations only, loci-only writer, append-only corrections, per-card FSRS for scheduling + per-concept state for estimation).
- D39. (Superseded by D43.) Inbox classification: explicit signals first (kind: override, clipper source: URL, non-markdown file, links.md), default draft; the agent flags but never silently overrides; kind + deciding rule shown in the review summary.
- D40. Keep the name views/.

## 2026-10-30 (after reviews, see reviews/00-synthesis.md)
- D41. (Superseded by D73.) Review workflow: the agent never commits. `loci inbox take` snapshots the inbox as the user; the agent edits the working tree; the user reviews `git diff`; `loci accept` lints and commits touched paths as `loci-agent`; `git restore` rejects. One pending job at a time. Event-producing commands commit the event file immediately. Lint never blocks the user's own commits. (Replaces agent branches in D5; D5's promotion gate is now `loci accept`.)
- D42. Deferred until data or need: event snapshot cache, exposure boost + calibration (until >=64 reviews), `relations.toml` format (`prereqs` built in until a second type is approved), GROBID, `searched`/`confused` events, `export` (to M4).
- D43. Inbox is split by folder: `inbox/drafts/`, `inbox/journal/<stream>/`, `inbox/sources/`; files at the inbox root are flagged. New journal entries only enter through `inbox/journal/`. Replaces the classification rules in D39.
- D44. Only concept slugs are vault-unique; other links carry a root-relative path. The H1 is the title (no `title:` field); `created:`/`verified:` dropped (time comes from git and events).
- D45. (Reading-note part superseded by D69.) Concepts may cite `journal/` as well as `sources/` and `commit:` refs. "Immutable" covers source material only; `note.md` is the user's writing. Taught notes cite a fetched source or are listed as unsourced.
- D46. (Tag part superseded by D65.) Migration adds a `legacy` record kind (link checks only), a `pre-loci` tag, and saved mtimes (`migration/mtimes.tsv`) that seed `authored` events.
- D47. Scheduling uses FSRS-6 via the `fsrs` crate 6.6.x (21 parameters, one stability; an earlier claim that the crate defaults to FSRS-7 was wrong, corrected after checking the source); the concept-level update is labelled uncalibrated.
- D48. PDF extraction tools are packaged with Nix (no containers). Extracted text is a cache in `.loci/`.
- D49. (Roadmap superseded by DESIGN §11.) Roadmap: M0 parser/lint/find/mv + mechanical migration; M0.5 status/accept/inbox take + home-manager module; M1 draft+journal ingest with a pilot area and bench; M2 PDF ingest; M3 learning; M4 full migration + export; M5 code.
- D50. Reading a PDF reader's own annotation store (e.g. sioyek's database) is deferred until loci is built and the vault migrated; v1 reads exported annotated PDFs.
- D51. PDFs are committed to the vault repo (no LFS, no external store).
- D52. "Learn X" starts from material the user doesn't understand: identify its concepts, resolve them against the KB, and expand unknown ones by searching external material (filed as sources) until every branch reaches the KB boundary (known or fading concepts) or a budget; the user prunes the plan, fading boundary concepts get a diagnostic, teaching goes boundary-inward, and ends by re-reading the material.
- D53. loci is open source; the vault is private. Public docs contain no vault content, paths or statistics; vault-specific notes live in the gitignored `private/` (later in the vault). Development tests use unit tests, handwritten fixture vaults, golden and property tests, a scale generator, and a sample vault from openly licensed material; the real vault is the final battle test.
- D54. External projects (code repos, paper/slide projects) are deferred in this version: no project references, anchors or drift checks; notes mention projects in prose or plain URLs. Candidate design kept in research/06. Supersedes D23's code plan for now.
- D55. No `loci upgrade`. The package ships AGENTS.md and skills under share/loci/; a Nix home-manager module symlinks them into the vault (gitignored there); `loci status` fails if they are missing or version-mismatched.
- D56. loci reads no signal from hister (no query logs, no opened-result counts, no bench cases from it). hister is only the user's phone/browser search UI over the vault.

## Rationale notes (moved from DESIGN.md, 2026-10-30)

- **Self-citation ban (D5, D59).** A widely reported failure of LLM-maintained wikis is a bad page that later pages cite until it becomes an accepted prior (source: a blog digest of the LLM-wiki gist's comments; research/02 §2). Hence evidence only from committed content and never concept→concept citations.
- **No persistent search index (D13).** Agents using only grep and file reads match or beat retrieval pipelines on many, but not all, benchmarks (Direct Corpus Interaction preprint 2026; Letta filesystem benchmark; Claude Code anecdote) on corpora of 100k+ documents — a favourable extrapolation to a personal vault. A flat one-level index degrades slowly as corpora grow; deep routing wastes context (He et al., ACL REALM 2026). Dense vs BM25 results are mixed (BrowseComp-Plus vs SAGE). A persistent index (deterministic rebuild, hard error on embedding-model change — lessons from Basic Memory and Smart Connections bugs) is added only if `loci bench` shows misses it fixes.
- **LLM-proposed prerequisites are suggestions (D29).** Zero-shot accuracy ≈0.75, F1 ≈0.78 (Graphusion); human raters also disagree on direct vs transitive edges (research/04).
- **User approves every card (D11).** Kirkby & Matuschak (2026) found about a third of LLM-drafted cards unusable.
- **Only graded recall feeds the estimate (D27, D58, D69).** No validated method estimates knowledge from notes alone; behaviour-only models track engagement, not mastery (research/02 §5, research/05). Exposure (authoring, annotating, rereading) is unread in v1 and its timing is in git; revisited once calibration data exists. Searches and browsing are not used (D24, D31, D56).
- **FSRS-6 (D47).** Verified in the `fsrs` 6.6.2 crate source: 21 parameters, one stability. The optimizer needs ≥64 training items.
- **Learn-X parameters (D52, D58).** Item counts, budgets and session lengths are starting values from research/05, not tested results; the sort step exists because right after migration almost no note has graded history.
- **H1 required.** hister uses the first `# ` line as the result title.
- **No tags (D15).** Areas, aliases, hub-concept links, views and the inbox cover every job tags did; LLM-written tags drift into synonyms; most `#word` tokens in real vaults are code.
- **Sources are folders with `source.yaml` (D69, D72).** One provenance rule for every file type; the hash is kept only for fetched files to detect a changed remote.
- **CJK (D74).** CC-CEDICT data (used by lindera's Chinese dictionaries, including `embed-jieba`) is CC BY-SA 4.0 and cannot ship in the MIT binary; jieba-rs bundles an MIT dictionary. Measured sizes and API fit with tantivy 0.27: research/07. Accepted limitations: a kanji-only Japanese query is segmented as Chinese; queries and notes can be split differently.
- **Agent compatibility (D60).** Checked against vendor docs (2026-10): Claude Code reads AGENTS.md only without CLAUDE.md and loads skills from `.claude/skills/`; Gemini CLI needs a settings change; Codex, Cursor, Copilot, opencode read `.agents/skills/`. Cloud agents lack gitignored symlinks, hence skills compiled into the binary.
- **From carrel.** Adopted: one-line digests and a budgeted root index; changes through link-preserving commands with permanent ids; immutable sources; rule files separate from framework rules; a recall benchmark. Not adopted: numeric folder ids (the user links by name), organising around the agent's memory (loci organises around the user's knowledge), one item per material (the canonical unit is the concept).
- D76. No `<!-- loci: … -->` directives: requests go to the agent directly (supersedes the directive part of D9 and §5 intake). Curated views are plain files in `views/`, created by the user directly, by asking the agent (built from digest/find/closure), or from a dropped draft whose value is an arrangement of existing concepts. The inbox is for material that needs processing; concepts, journal entries and views may be edited directly.
- D77. Round-4 cuts: no `resolve` event (a dispute is re-judged at once; only the final grade is logged); no event idempotency key; source origins are only `fetch` and `inbox` (clippings come through the inbox), every `source.yaml` has a SHA-256 checked by lint (`sources.hash-mismatch`), replacing the diff-vs-HEAD `sources.modified` rule and the `file` key; a re-annotated PDF's annotations are processed and the new copy deleted, the filed original unchanged; no lint tree mode; `closure` reads the working tree; `migrate verify` replays in memory; no `mtimes.tsv` (users save file times themselves if wanted); `mv` does not rewrite file-relative legacy links; `loci status` warns (not fails) on missing skill links; cards may be multi-line; journal entries have no frontmatter; `merge` is M1; M0 spec's M3 appendix removed (M3 gets its own spec); specs are prescriptive only. The rule for admitting new relation types (D29) and the M3 evaluation questions live here and in the roadmap, not in DESIGN's data model.
- D78. Round-5 cuts: sources are not link-checked; `origin: inbox` records only SHA-256 (no snapshot, no `fetch.uncommitted`); `commit:` citations use full 40-hex SHAs; no info severity; `size.note` counts all characters; no lint totals in `status`; no `init --stream`; sub-areas have no AREA.md; `status` warns on missing skill links. Learn-X counts (questions, diagnostic items, rubric points, concepts per session, cards per concept) live in the learn skill as starting values (research/05), not in DESIGN.
- D79. Legacy is the folder `legacy/`, outside the system: not linted, ignored by digest/closure/learner, searched as plain text by `find`; links into it are checked only for file existence. Migration is `git mv` of the old tree into `legacy/` and then agent work area by area until it is empty. Deletes `loci migrate plan|apply|verify`, the plan format, verify, `migration.legacy` and every legacy-specific lint rule (supersedes D46, D65 and the migration parts of D72/D77). The first real-vault test becomes the M1 pilot.
- D80. No legacy concept at all (supersedes D79): migration creates a new vault; the old notes repo stays outside, untouched; area by area the user copies old notes and images into the new vault's inbox folders and the agent processes them with the normal intake. No `legacy/` folder, no legacy lint exceptions, no special name-resolution rules. M0 is done when fixture, golden and property tests pass; the first real-vault test is the M1 pilot.
- D81. Keep the `material-dropped` warning: a count-based check (math spans, images, code blocks in deleted files vs added/edited files, against HEAD) that catches content an agent loses while dissolving drafts. Known limits: false alarms when duplicates are consolidated, misses when a loss is offset by an unrelated addition. Kept because migration volume makes diff-review fatigue likely; it is a warning, never a block.
- D82. Round-6 fixes: bare `[[name]]` resolves only to concept slugs (other targets use vault-root paths); aliases are for search and duplicate checks, never link resolution; vault notes and images use wikilinks only, markdown links only for external URLs; `git add -N` is a skill rule only; `init` never commits and creates no empty folders (no `.gitkeep`); no `ignore.missing`, no frontmatter quote-style rule; `source.yaml` = SHA-256 (+ URL if fetched), file type by extension; `find` (not `status`) warns about missing CJK dictionaries when it meets CJK text; each lint rule ships with the milestone that introduces what it checks; cards and block ids are parsed from list-item/paragraph raw byte ranges (pulldown-cmark emits no Paragraph inside tight list items); discard is `git reset --hard` (`git restore` leaves empty intent-to-add files — tested).
- D83. Card ids are assigned only by `loci card-ids` (OS randomness, redrawn on collision within the note; never touches existing ids); cards are written without ids and `card.no-id` is a lint error with that hint. A meaning change = delete the id and re-run. Reason: a model cannot generate real randomness and may reuse a deleted card's id, silently attaching old review history to a new question; 30 random bits make reuse of a past id negligible. M0.5.
- D84. `loci card-ids` also redraws any id whose global card id appears in the event log, so an id with review history is never reused (only reused ids with history cause harm). This makes reuse impossible rather than improbable (6 base32 chars = 2^30 per note; expected reuses without the check ≈ 0.01 over 100k cards). Keeps 6-character ids for readability. Note for the M1 `merge` spec: moving cards between notes must redraw ids that collide in the target and log `alias` events.
- D85. Card ids are vault-unique block ids (no concept prefix); `card.id-duplicate` is vault-wide; `loci card-ids` checks all concept notes and the event log. Moving a card between notes keeps its id and history, so card-level `alias` events and merge collision handling are unnecessary.
- D86. The learner event log becomes the review log: a single file `learner/reviews.jsonl` (no yearly shards), one record kind (a graded recall: card or concept, purpose, grade, grader, verdicts, item), no `alias` events, no event ids or types. Git versions files but cannot record a review that changes no file; a current-state file would lose the per-card review history FSRS fitting and evaluation need, and state in notes would put scheduling noise in diffs. A merge deletes the absorbed note; its quiz-only history stops counting. Spec renamed to specs/review-log.md.
- D87. Learning is a plugin. Workspace crates `loci-core` (library API), `loci` (core CLI), `loci-learn`. Git/cargo-style dispatch: `loci <name>` runs `loci-<name>` from PATH with `LOCI_VAULT`/`LOCI_VERSION`. Plugin contract: `--json` envelope; data only under `plugins/<name>/` (core ignores it); optional `lint --json` merged by `loci lint` (codes prefixed `<name>.`); optional `skills` listed by `skill show`; refuse on major version mismatch. Cards, card ids, the review log (now `plugins/learn/reviews.jsonl`), estimates and the learn skill move to the plugin; core treats `## Cards` as markdown. Reason: estimates have only two readers, both learning; the boundary keeps core small and building a real plugin early shapes the `loci-core` library API.
- D88. Block ids are a generic core feature; `loci block-ids <note> [--section <h>]` (M0.5) assigns 16-char Crockford base32 ids (80 random bits), redrawn on a current-vault match, never touching existing ids. Cards are a learn-plugin convention on top (list items under `## Cards` whose block id is the card id); the plugin lints them and never writes notes, writing only `plugins/learn/` (`reviews.jsonl`, `config.toml` with `new_per_day`). Review appends each grade immediately and commits the log once per session. Reason: keeps the plugin contract strict (read vault, write `plugins/<name>/`) without making non-learning users pay for cards; block ids are a widely accepted markdown feature. ID size: lifetime reuse probability of a past id with history ≤ ~2^-40 under generous bounds (2^20 draws × 2^20 past ids, 80-bit ids), the same random size as a ULID. Supersedes D83–D85 and the card parts of D87.
- D89. Generated block ids are ULIDs (ulid/spec; same format as concept ids; `ulid` crate) instead of a custom 16-char scheme — a published standard with the same 80 random bits, valid as markdown-oxide block ids (`\w+`), and records creation time. UUIDs/NanoIDs were rejected because `-` is not `\w`. A list item's block id sits at the end of its leading text, before nested lists, and identifies the whole item (so items with nested lists can carry ids).
- D90. - D100. Kanji-only query runs are also segmented with IPADIC when the `ja` dictionary is compiled in, and those tokens are added to the OR query. This removes the limitation D74 had accepted: a kanji-only Japanese query such as `勉強` was split by jieba into `勉`/`強` and missed text that IPADIC had indexed as `勉強`. The run's language is guessed from its script, and kanji carry no language signal. The change is on the query side only, so the index is unchanged; the cost is a little extra recall noise for Chinese queries in builds with `ja`. Rejected alternatives: indexing kanji-only text both ways (more index noise) and a per-note language field (a new concept).
- D101. Chinese and Japanese are segmented by ICU4X's word segmenter (`icu_segmenter` 2.x, compiled data, always built in), replacing jieba-rs and lindera IPADIC (the `zh` and `ja` features). Korean keeps lindera ko-dic behind `ko`.
  - **Why.** ICU's one dictionary (`cjdict`) covers both languages, so a query and a note are split alike and a kanji-only word no longer depends on a guess about the run's language. This supersedes D100's query-side workaround and the routing part of D74.
  - **Licence and size.** `cjdict` is built from Libtabe and IPADIC (permissive, no CC-CEDICT, per ICU's LICENSE), so it ships in the MIT binary with notices (`THIRD_PARTY_NOTICES`). The Nix binary drops from 146 MB to 100 MB, nearly all of it ko-dic.
  - **Why ko-dic stays.** ICU4X follows UAX #29, which keeps a space-separated Korean word (particles and endings included) whole, so it cannot replace ko-dic.
  - **Open.** Ranking quality on real Chinese and Japanese notes is unmeasured; jieba's overlapping `cut_for_search` tokens are gone. Re-check with `loci bench` cases after migration (research/09).
- D102. Korean text is indexed as Hangul syllable bigrams; ko-dic, lindera, the `ko` feature, the Nix dictionary download and `find.no-dictionary` are removed (supersedes the Korean part of D101).
  - **Why not whole words.** UAX #29 keeps a space-separated Korean word whole, particles and endings included, so `공부` would never match `공부했습니다`.
  - **Why bigrams.** They match without a dictionary, split a query and a note alike, and cut the release binary from 101 MB to 19 MB.
  - **Costs.** Some precision is lost, and a one-syllable query matches only a one-syllable run. This is the same scheme Lucene's CJK analyzer uses for Hangul.
- D103. Concepts no longer cite dissolved drafts (`commit:<sha>:<path>` is removed as a source form), and the `concept.unsourced` warning is removed.
  - **Why.** The intake commit already deletes the draft and writes the concepts together, so `git log -p -- <concept>` recovers the original text.
  - **What the citations cost.** They broke on squash, rebase and shallow clones (`sources.unresolved`), added 40-hex noise to frontmatter, and existed partly to keep notes written from the user's own drafts from being flagged as unsourced.
  - **What `sources` holds now.** Only `sources/` and `journal/` evidence.
  - **Unchanged.** Inbox files must still be committed before intake, so a dissolved draft can be recovered.
- D104. Source types and journal streams are user-named: any slug folder under `sources/` or `journal/` is a type or a stream. Nothing is declared in `loci.toml`.
  - **Why.** The fixed list (`papers`, `docs`, `clippings`) carried no behaviour: page citations depend on the file extension, not the type. It only made books, talks or datasets lint errors.
  - **What lint checks.** The type, the source folder's slug and the journal stream must be slugs (`sources.layout`, `journal.path`). Before this, lint checked none of them.
- D105. Journal entries have no imposed name or folder format: any `.md` file inside `journal/<stream>/` (the stream a slug) is an entry. This replaces `YYYY/MM/YY-MM-DD[-slug].md`.
  - **Why.** Nothing reads the date; timelines come from `git log`. The pattern repeated the year and month, and it forced migrated diaries to be renamed.
  - **What agents do.** New entries follow the names already used in their stream. In a new stream the agent asks the user how to name entries and records the answer in `RULES.md`. Lint only reports a file outside a stream, or a stream that is not a slug (`journal.path`).
