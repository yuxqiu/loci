## 2. Architecture

### 2.1 Workspace

One cargo workspace with four crates:

| Crate | Kind | Contents |
|---|---|---|
| `loci-core` | library | vault model and kinds, parser and spans (§4), link resolution (§5), splice editing (§4.5), git helpers, the `--json` envelope types (§8), the lint diagnostic type, plugin protocol types (§2.3) |
| `loci` | binary | the core CLI (§9) and plugin dispatch (§2.2) |
| `loci-learn` | binary | the learn plugin (`docs/specs/learn-plugin.md`) |
| `loci-testkit` | library (dev-only) | test vaults and envelope helpers shared by the `loci` and `loci-learn` tests |

`loci-core` and `loci` never depend on a plugin crate. A plugin depends on
`loci-core` and on nothing else from the workspace. All crates share one version,
`workspace.package.version`.

### 2.2 Dispatch

A **plugin** is an executable named `loci-<name>` on `PATH`, where `<name>` matches
`^[a-z][a-z0-9-]*$` and is not a core command. The first match on `PATH` wins.

`loci [--vault <dir>] [--json] <name> <args>...`, where `<name>` is not a core
command, runs `loci-<name> <args>...` (with `--json` appended if it was given before
`<name>`), passes stdin, stdout and stderr through, and exits with the plugin's exit
code. Dispatch requires a vault, found as for core commands (§8, global options);
without one it exits 1 with `vault.not-found`. The environment adds:

- `LOCI_VAULT`: the absolute vault root;
- `LOCI_VERSION`: the core version (`CARGO_PKG_VERSION` of `loci`).

If no `loci-<name>` is on `PATH`, `loci` exits 1 with `cmd.unknown`, listing the
core commands and the installed plugins.

### 2.3 Plugin contract

1. **Envelope.** Every plugin command supports `--json` and prints the core
   envelope (§8), using the `loci-core` types. Exit codes are those of §8.
2. **Data.** A plugin binary writes nothing outside `plugins/<name>/`. (Content the
   agent writes while following a plugin's skills is ordinary vault content.) Core `init` writes
   nothing plugin-specific.
3. **Lint (required).** `loci lint` runs `loci-<name> lint --json` for every
   installed plugin, with the environment of §2.2, and merges the plugin's
   `diagnostics` into its own. The plugin's `data` is `null`. Every plugin rule code
   starts with `<name>.`. A plugin with nothing to report prints no diagnostics.
4. **Skills (required).** `loci-<name> skills --json` prints `data: {"skills":
   [{"name", "description", "body"}]}`, possibly empty. Every skill name starts
   with `<name>-`.
5. **Failure.** If a plugin's `lint` or `skills` exits with a code other than 0 or 1,
   prints an invalid envelope, returns a non-null `error`, or reports a code without
   its `<name>.` prefix, core
   reports `plugin.failed` (error, naming the plugin and the reason) and uses none
   of that plugin's output for that command.
6. **Version.** A plugin requires `LOCI_VERSION`: when it is unset, the plugin exits
   1 with `plugin.direct` ("run as `loci <name>`"); when `LOCI_VAULT` is unset, it
   exits 1 with `vault.not-found`. It refuses to run (`plugin.version`, exit 1) when
   `LOCI_VERSION` is not semver-compatible, by Cargo's rule, with the workspace
   version it was built with.

## 3. Vault model

The vault is a git work tree whose root contains `loci.toml`. A file's **kind**
comes from its path only:

| Kind | Code | Paths |
|---|---|---|
| concept | C | `concepts/<area>/**/<slug>.md`, except `AREA.md` |
| area | A | `concepts/<area>/AREA.md` |
| view | V | `views/**.md` |
| journal | J | `journal/**.md` |
| rules | R | `RULES.md`, `STYLE.md`, `AGENTS.md` at the root |
| source | S | every file under `sources/` |
| inbox | N | every file under `inbox/` (drafts live in `inbox/drafts/`) |

C, A, V, J and R are the **managed** kinds. Any other `.md` file is `kind.unknown`.
The vault's files are the ones git sees:
tracked files, and untracked files that no ignore rule matches (`.gitignore`,
`.git/info/exclude`, the user's excludes file). So ignored paths (including
`.loci/`), `.git/`, `plugins/`, the root `loci.toml` (read only as configuration) and
the root `.gitignore` are never read as vault files, and a tracked file is read even
if an ignore rule matches it.

**No symlinks.** loci never reads or writes through a symlink, whose target may be
outside the vault. Opening the vault lists its files once (the list every command
uses), and a vault in which any listed path (`plugins/` and `loci.toml` included)
is a symlink or lies under one is refused by every command with `file.symlink`
(exit 1), naming each link. If git cannot list the vault at all, every command is
refused with `git` (exit 3): no command runs on a guessed file list. Replacing
each link with the file or folder itself makes the vault usable again. `init`, which
runs before there is a vault, refuses the same way if a file it manages is a link.

**Every file readable.** Opening the vault also reads every `.md` file core reads.
A vault in which any file core reads cannot be read (no permission, or inside a
folder without permission, or a folder git cannot list), or a `.md` file is not
valid UTF-8, or a path git tracks as a file is now a FIFO, socket or device (opening
one can block), is refused by every command with `file.unreadable` (exit 1), naming
each. A listed path that is a folder is skipped: a submodule, an untracked nested
repository, or a tracked file that became a folder, whose files git lists on their
own. So is a vault where git lists any name that is not UTF-8, anywhere
(`plugins/` included) and whether or not the file is still on disk: every vault
path is UTF-8. No command meets an unreadable file, so none can mistake one for a
missing one. The contents of files core never reads (`plugins/` and the others
above) are not checked, but a folder git cannot list refuses the vault wherever it
is, `plugins/` included: loci cannot tell what git left out.

All paths are fixed: `concepts/`, `views/`, `journal/`, `sources/`, `inbox/` (with
`drafts/`, `journal/<stream>/`, `sources/`), `plugins/<name>/`, `bench/`,
`.loci/`, `RULES.md`, `STYLE.md`, `AGENTS.md`. Folders are created on
first use.

Sub-folders of an area (`concepts/<area>/<sub>/`, at any depth) may exist; they
have no `AREA.md` (a file named `AREA.md` in a sub-area is a concept and fails
`slug.format`).

**Block ids** are markdown-oxide `^id` markers at the end of a paragraph or list
item (§4.6), matching `^\w+$` (Unicode `\w`). A block id is unique within its note
(`block.id-duplicate`); vault-wide uniqueness is not a core rule. They are written by
hand or generated by `loci block-ids` (§9.9); a generated id is an ordinary block
id.

## 4. Parsing and spans

### 4.1 Input

- Every `.md` file is read once, as UTF-8 text, when the vault is opened; a file
  that cannot be read refuses the vault (`file.unreadable`, §3).
- A UTF-8 BOM is `file.bom` in managed kinds and is skipped elsewhere.
- Line endings are preserved by splicing.
- File names must be NFC (`path.not-nfc`).

### 4.2 pulldown-cmark

Options: `ENABLE_WIKILINKS | ENABLE_MATH | ENABLE_YAML_STYLE_METADATA_BLOCKS |
ENABLE_TABLES | ENABLE_FOOTNOTES | ENABLE_STRIKETHROUGH | ENABLE_TASKLISTS`.
Never `ENABLE_HEADING_ATTRIBUTES`, `ENABLE_SMART_PUNCTUATION`, `ENABLE_GFM`,
`ENABLE_SUPERSCRIPT`, `ENABLE_SUBSCRIPT`. All ranges come from `into_offset_iter()`
and are byte ranges. Inline `#hashtags` are text.

### 4.3 Frontmatter

The frontmatter is pulldown's `MetadataBlock` at offset 0 (after a BOM). A file whose
first line is `---` but which has no such block is `fm.unterminated`.

The YAML text is parsed with `saphyr::MarkedYaml::load_from_str`. The top level must
be a mapping; otherwise, and on parse errors (including duplicate keys, which saphyr
rejects), `fm.yaml`.

### 4.4 saphyr spans

`Marker::index()` counts characters. For each frontmatter block, build one
char-index→byte-offset table and convert every span through it. Scalar spans include
their quotes. Flow-sequence spans end before `]`.

### 4.5 Splice API

```rust
struct Edit { range: Range<usize>, new: String }   // byte range into the original
fn apply(original: &str, edits: Vec<Edit>) -> Result<String, EditError>;
```

Edits are sorted by `range.start` and must not overlap (zero-length inserts at the
same offset are applied in input order, and before a replacement starting there);
overlap is an error. Every mutating command
builds all edits for a file from one parse, applies them in one pass, and never
re-parses mid-edit. Frontmatter is never re-emitted by `YamlEmitter`: edits change
only the bytes they target.

### 4.6 Headings and block ids

pulldown emits no `Paragraph` events inside tight list items, so block ids are read
from raw source slices of block byte ranges.

- **Heading text** is the raw source of the heading content, trimmed: ATX `#`
  markers and closing `#`s removed, setext underline excluded, inline markup kept
  raw.
- **Leading text** of a list item: its first paragraph, including lazy and indented
  continuation lines, up to the start of any nested list or other nested block (or
  the end of the item). In a loose item it is the range of the item's first
  `Paragraph`; in a tight item, the range from the item's content start to the
  first nested block's `Start` (or the item's `End`).
- **Block id:** matched by `(?:^|\s)\^(\w+)\s*$` on a raw source slice.
  - A **list item's** block id sits at the end of its leading text and identifies
    the whole item, including its nested children. A nested child item carries its
    own id the same way.
  - A **paragraph's** block id (a paragraph outside list items, or a later paragraph
    inside an item) sits at the end of the paragraph.

  Tight and loose lists give the same result.

### 4.7 Parse result and reads

One parse per file yields: kind, frontmatter (range, marked YAML), headings (level,
raw text, byte range), H1 list, list items (byte range, nesting depth), block ids,
and links. Each link records its form, its byte range and the byte range of its
target (§5.1), the raw target and the fragment; the index resolves it (§5.3). `loci-core` exposes this structure to the core commands and to
plugins.

Every command reads the vault's file list made when the vault is opened (§3), with
`git ls-files --cached --others --exclude-standard`; a warning git prints while
listing (a folder it cannot open) refuses the vault (`file.unreadable`, §3).
`material-dropped` takes the current counts from this parse and reads the `HEAD` blob
of each changed path with `git cat-file blob`.

## 5. Links and resolution

### 5.1 Extracted forms

Ignored inside code spans, code blocks, math, HTML blocks and inline HTML.

| Form | Where | Meaning |
|---|---|---|
| `[[target#frag\|label]]` | body | link to a vault note or file |
| `![[target#frag\|size-or-alt]]` | body | embed (image or note) |
| `[label](url)`, `![alt](url)` with a URL scheme | body | external; not checked |
| `[label](path)`, `![alt](path)` without a URL scheme (inline or reference) | body | `link.markdown` in managed kinds; never resolved |
| `prereqs:` items `"[[slug]]"` | frontmatter | concept link |

Vault targets use wikilinks only: `[[…]]` for notes, `![[…]]` for images and other
files. A markdown link or image to a vault path is `link.markdown`, with the hint to
use the wikilink form. Autolinks and HTML (including `<img>`) are not links.

**Target byte range.** For wikilinks, pulldown's `dest_url` includes the fragment,
and for a piped link the `Text` child covers only the label. The target range is
computed from the `Start` range: from `start + 2` (`+ 3` for `![[`) to the first `|`
or `]]`. For `prereqs` it is the scalar span minus the quotes and the `[[`/`]]`.

### 5.2 Normalisation

In order:

1. Strip one trailing `\` (a wikilink in a table is written `[[x\|y]]` and yields
   `dest_url = "x\"`).
2. Trim ASCII whitespace.
3. Split off `#fragment`.
4. Strip one trailing `.md`.
5. Unicode NFC.

`[[]]` is not a link.

### 5.3 File resolution

- **Target has no `/`: concept slug.** The target is compared, exactly, with the
  concept slugs. A match resolves to that concept; no match is
  `link.dangling`, with a hint naming the closest concept slug ("did you mean
  `[[<slug>]]`?", Jaro-Winkler similarity at least 0.85 with the target in lowercase,
  so `[[BFS]]` suggests `[[bfs]]`) or, when none is close,
  saying to create the concept with `loci new` or link a non-concept by path. A slug shared by
  several concepts (`slug.duplicate`) resolves to none of them: `link.dangling`,
  with a hint naming them and asking for a path link.
- **Target contains `/`: path.** Match exactly and case-sensitively against vault
  paths: without `.md` for notes, with the extension for other files. Files under
  `plugins/` are not link targets. A `..` segment or a leading `/` is
  `link.path-form`.

### 5.4 Fragments

- `#^id`: the target note must contain block id `id` (exact, case-sensitive);
  otherwise `link.dangling-block`.
- `#text`: matches if `lowercase(text).replace(' ', '-')` equals
  `lowercase(heading).replace(' ', '-')` for any heading of any level in the target,
  with heading text as in §4.6. Otherwise `link.dangling-heading`, whose hint lists
  the target's headings (no fix: choosing one is judgement). A missing block is
  `link.dangling-block`, whose hint says the block was removed or its id changed.
- A link that is only `#fragment` is checked against the linking note's own headings.
- Embeds of non-markdown files: the fragment is not checked. The part after `|` in
  an embed is a size (`300`, `300x200`) or alt text, never a label.

### 5.5 Citations

A concept cites its evidence with ordinary links in its text, next to the claim they
support: `[[sources/<type>/<slug>.<ext>#p3]]` for a page of a PDF (the fragment of
a non-markdown file is not checked), `[[sources/<type>/<slug>#heading]]` for a
heading of a markdown source, or a path to a journal entry. There is no `sources:`
field.

## 6. Frontmatter and file formats

### 6.1 Frontmatter by kind

| Kind | Frontmatter |
|---|---|
| concept | `id` (required), `prereqs`; nothing else |
| area, view, journal, rules | none (`fm.not-allowed`) |
| source, inbox | not checked |

- `id`: a 26-character Crockford base32 ULID, uppercase.
- `prereqs`: list of quoted strings, each exactly `"[[<slug>]]"`. Anything else
  (including an unquoted `[[x]]`, which parses as a nested list) is `fm.field-type`
  with the hint `write "[[slug]]"`.
- `prereqs` items are written without escape sequences or line folding, so their
  bytes in the file are their value (`fm.field-type` otherwise); `mv` and `merge`
  edit them in place. Other items are not links.

### 6.2 Slugs and names

A concept's slug is its file stem. It must match
`^[\p{Ll}\p{Lo}\p{N}]+(-[\p{Ll}\p{Lo}\p{N}]+)*$`, so lowercase Latin and CJK slugs
are both legal (`binary-search`, `二分查找`). A slug is written exactly, in links and
arguments as in the file name: `[[BFS]]` does not name `bfs.md`. A concept whose stem is not a slug (`a_b`, `BFS`: `slug.format`) has
none: no bare link or slug argument names it, only its path. Two concepts with the
same slug are `slug.duplicate`. Only concepts
take part: `views/learn/<concept>.md` may share a concept's stem. A concept has no
other names: an abbreviation, a spelling or a translation belongs in its H1 or
text, where a search finds it.

### 6.3 AREA.md

Every area folder that contains a concept has `concepts/<area>/AREA.md`, written by
the agent:

```markdown
# Algorithms

Techniques for searching, sorting and traversing data, with their cost models.
Data structures studied for their own sake belong in [[concepts/data-structures/AREA]].
```

No frontmatter, exactly one H1 (the area title), then exactly one paragraph and
nothing else. The paragraph is at most `budgets.area_paragraph` characters. Links are
allowed and checked.

The paragraph is a scope note (research 13): what kinds of concept the area holds;
where a neighbouring area could be mistaken for it, which topics go there instead,
linked as `[[concepts/<other>/AREA]]` (the other area says the same in return); and,
optionally and briefly, key topics that have no sub-folder. It does not list
sub-folders (the folder itself shows them), summarise concepts or record
history. Only top-level areas have an `AREA.md`; a sub-folder that needs its own
scope note becomes an area (`loci mv`).

### 6.4 Sources

Every source is one file `sources/<type>/<slug>.<ext>`, where `<type>` and `<slug>`
both follow §6.2 and `<ext>` is lowercase ASCII letters and digits with at least one
letter (`pdf`, `md`, `mp3`). Types are not declared: any slug is a type, chosen by the user (for
example `papers`, `docs`, `clippings`, `books`). A source's format comes from its
extension: `.md` is markdown, `.pdf` is PDF, anything else is an opaque document.
A source is filed by moving an inbox file there with `loci mv` (§9.5) or by
downloading it there directly; where it came from is not recorded.

Sources never change. Lint, per file:

- A file under `sources/` that is not `sources/<type>/<slug>.<ext>`: `sources.layout`.
- A source whose content differs from HEAD at the same path: `sources.changed`. Git
  holds the original. Renaming or deleting a source is not a change to it; a
  citation that no longer resolves is a link error.

### 6.5 Rule files

`RULES.md` (vault rules, with a `## Lessons` section the agent maintains) and
`STYLE.md` (the user's writing style) are plain markdown with no ids and no schema.
The agent reads them at the start of a session, as the `AGENTS.md` stub says (§9.1).

### 6.6 Journal paths

A journal entry is any `.md` file inside `journal/<stream>/`, where `<stream>`
follows §6.2. Folders and file names below the stream are the user's choice; no
date format is imposed. Streams are not declared: any slug is a stream, created on
first use. A file directly in `journal/`, or in a stream whose name is not a slug,
is `journal.path`.
Journal entries have no frontmatter; the agent adds concept links in the body only.

## 7. Lint

### 7.1 Severities and output

- `error`: exit 1. Lint reports every error in the working tree.
- `warning`: reported only.

Lint never blocks a commit. Diagnostics, core and plugin together, are sorted by
(path bytes, byte offset, code); two runs on the same tree give byte-identical
output. Vault-level rules report on the first involved path in that order and name
the others in the message. Messages contain no line numbers or byte offsets (those
are separate fields).

### 7.2 Which files are linted

The "Applies to" column of §7.3 says which files each rule covers. Sources are not
link-checked; they are link targets only.

### 7.3 Rules

A rule ships with the milestone that introduces the files or workflow it checks.
Plugin rules are specified by each plugin.

**Editions.** A vault's edition is its `updates` mark (§11; updates spec §3). The core
rules are one table, `lint::RULES`: each row lists the codes its check reports and
the editions it applies to (`Editions { from, until }`: the vaults that have handled
`from` and not `until`). Format facts that change over time are tables with the same
column, starting with `lint::CONCEPT_FIELDS` (§6.1). A vault update that removes
something sets `until` to itself on its row: before the vault handles the update, the
old form is valid and a generic rule reports it as outdated, `update.<id>` (a
warning, with the fix the update applies); after, the current rules judge it
(`digest:` is then `fm.unknown-field`). Adding a rule is adding a row; a rule an
update retires gets `until` that update.

| Code | Sev | Applies to | Milestone | Message (template) |
|---|---|---|---|---|
| `path.not-nfc` | E | every file | M0 | file name is not in Unicode NFC |
| `file.bom` | E | managed | M0 | file starts with a byte-order mark |
| `kind.unknown` | E | unmatched `.md` | M0 | file is outside every known folder |
| `fm.unterminated` | E | managed | M0 | frontmatter opened with `---` is not a closed block |
| `fm.yaml` | E | managed | M0 | frontmatter is not a YAML mapping: `<reason>` |
| `fm.not-allowed` | E | A V J R | M0 | `<kind>` files have no frontmatter |
| `fm.unknown-field` | E | C | M0 | field `<key>` is not allowed in a concept |
| `update.<id>` | W | as the update | M0 | vault update `<id>` removes the concept field `<key>` (before the vault handles `<id>`; unsafe fix deletes it) |
| `fm.field-type` | E | C | M0 | `<key>` must be `<type>` |
| `fm.missing-field` | E | C | M0 | concept has no `id` |
| `fm.id-format` | E | C | M0 | `id` `<v>` is not a ULID |
| `fm.id-duplicate` | E | vault | M0 | id `<v>` is used by `<paths>` |
| `h1.missing`, `h1.not-first`, `h1.multiple` | E | managed | M0 | no H1 / the H1 is not the first block after the frontmatter / more than one H1 |
| `slug.format` | E | C | M0 | slug `<s>` does not match the slug pattern |
| `slug.duplicate` | E | vault | M0 | slug `<s>` is used by `<paths>` |
| `area.missing` | E | vault | M0 | area `<a>` has no AREA.md |
| `area.format` | E | A | M0 | AREA.md must be an H1 and one paragraph |
| `area.too-long` | W | A | M0 | area paragraph is `<n>` characters (budget `<b>`) |
| `link.dangling` | E | managed | M0 | `<target>` does not resolve |
| `block.id-duplicate` | E | managed | M0 | block id `^<id>` appears more than once in this note |
| `link.dangling-heading`, `link.dangling-block` | E | managed | M0 | `<note>` has no heading `<frag>` / no block `^<id>` |
| `link.path-form` | E | managed | M0 | `..` or a leading `/` is not allowed in a link |
| `link.markdown` | E | managed | M0 | a vault target must use a wikilink: `[[<path>]]` or `![[<path>]]` |
| `prereqs.cycle` | E | vault | M0 | prereq cycle: `<a> → … → <a>` |
| `journal.path` | E | J | M0 | journal entry is not inside a `journal/<stream>/` folder whose name is a slug |
| `inbox.root-file` | W | N | M0 | file directly in `inbox/` or `inbox/journal/`; move it into `drafts/`, `sources/` or a journal stream |
| `size.note` | W | C | M0 | note body is `<n>` characters (budget `<b>`) |
| `plugin.failed` | E | plugin | M0 | plugin `<name>` `<command>` failed: `<reason>` |
| `sources.layout` | E | S | M0.5 | not a `sources/<type>/<slug>.<ext>` file |
| `sources.changed` | E | S | M0.5 | source `<path>` differs from its committed version |
| `material-dropped` | W | vault | M0.5 | deleted files held `<n>` `<category>` but only `<m>` were added elsewhere |
| `git.failed` | W | vault | M0.5 | git failed, `sources.changed` and `material-dropped` were not checked: `<reason>` (when `git status` fails) / git failed, `material-dropped` was not checked: `<reason>` (when reading `HEAD` fails) |

**`material-dropped`** compares the working tree with `HEAD`, and is skipped when
there is no `HEAD`. A changed path (from `git status`, renames split into a deletion
and an addition, file modes and submodules ignored) is deleted, added or modified by
whether it is in `HEAD` (`git ls-tree`) and on disk. Only vault files count (§3): a deleted path core
would read, and a current file in the vault's file list; `plugins/` never does. It runs per category (math spans, images, fenced
code blocks): *deleted* is the sum of counts in files deleted relative to `HEAD`;
*added* is the sum, over every other new or modified file, of
max(0, count now − count at `HEAD`). It warns where deleted > added.

### 7.4 Counting

- **Characters** are Unicode scalar values (`str::chars`).
- Every budget counts every character: `size.note` the note's body after the
  frontmatter; `area.too-long` the area paragraph.

## 8. `--json` envelope and exit codes

Every command, core or plugin, accepts `--json` and then prints exactly one JSON
document on stdout:

```json
{
  "schema": 1, "loci": "0.1.0", "command": "lint", "ok": false,
  "data": {"files": 42, "errors": 1, "warnings": 3},
  "diagnostics": [
    {"code": "link.dangling", "severity": "error",
     "location": {"path": "concepts/algorithms/binary-search.md",
                  "span": {"line": 12, "col": 5, "byte_start": 431, "byte_end": 449}},
     "message": "`sorted-aray` does not resolve", "hint": "no concept is named `sorted-aray`; did you mean [[sorted-array]]?"}
  ],
  "error": null
}
```

- `loci` is the version of the binary that prints the envelope; `command` is its
  command (`learn state` for a plugin, without the `loci-` prefix).
- `location` is the file a diagnostic is about, or `null` for the whole vault;
  its `span` is a position in that file, or `null`. A span has all four fields:
  `line` and `col` are 1-based, `col` counts Unicode scalar values, and byte
  offsets are exact. `hint` may be `null`. A plugin envelope whose diagnostics do
  not have this shape is invalid (`plugin.failed`).
- A diagnostic may carry `fixes` (omitted when it has none): each is
  `{"message", "applicability", "edits": [{"path", "byte_start", "byte_end", "new"}]}`,
  the best first; fixes edit text only (a rename is `loci mv`'s, so `path.not-nfc`
  carries the `mv` command as its hint). `applicability` is `safe` (keeps the meaning; `lint --fix` applies it),
  `unsafe` (a likely fix that may change meaning; `--unsafe-fixes`) or
  `display-only` (a starting point; never applied). A fix that inserts a new id
  carries a fresh ULID each run. Core fixes (§9.2): `link.markdown` (safe; unsafe for
  a percent-encoded URL), `fm.field-type` for an unquoted `[[slug]]` prereq,
  `fm.missing-field` and `file.bom` are safe; `link.dangling` with a close slug, `fm.id-duplicate` and `block.id-duplicate` are unsafe; an update check's
  fixes are as the update says (u0001's is unsafe);
  `h1.missing` is display-only.
- Every warning a command emits, including those of `status`, is a
  diagnostic.
- `error` is `{"code": "...", "message": "..."}` when the command could not do its
  work (refused precondition, I/O, git failure). Then `ok` is `false` and `data` is
  `null`.
- `ok` is `true` iff the exit code is 0.

Exit codes: **0** success; **1** a refused precondition (`error.code` set), or any
diagnostic of severity error, whichever command reports it; **2** usage error (from `clap`, no envelope);
**3** I/O, git or internal failure.

Without `--json`, the same content goes to stdout in a human format; command errors
go to stderr.

**Global options.** `--vault <dir>` (default: nearest ancestor of the working
directory containing `loci.toml`), `--json`. Every command, core or plugin, except core
`init` and `rules` requires `loci.toml` (`vault.not-found`) and that the vault root is the
root of a git work tree (`vault.not-git`). `loci.toml` errors are `config.invalid`
(exit 1).

**Which paths are vault paths.** Positional arguments name things in the vault and
are vault paths or slugs, resolved as a link target is (§5.3): from the vault root,
wherever loci is run. Options that take a file (`--vault`, `export -o`,
`bench --cases`), and `init`'s folder, which comes before any vault, are ordinary paths
relative to the working directory.

**Path arguments** are vault paths, normalized by the `relative-path` crate: `.`
segments and repeated or trailing `/` are dropped (`./a//b/` is `a/b`), each `..` steps back one
folder (`a/../b` is `b`; exact by name, since a vault holds no symlinks, §3), and the
path is put in NFC. A path argument that is absolute or whose `..` climbs above the
vault root is refused (`path.outside`, exit 1), and one that names the root itself
(`./`, `a/..`) too (`path.root`, exit 1).

**Note arguments** (in `block-ids`, `links`, `closure`, `export`, `merge` and
`loci learn state`) are path arguments naming a note: a vault path (`.md` optional)
or a concept slug (written exactly), resolved as a bare link is (§5.3). A slug
shared by several concepts is refused (`concept.ambiguous`, exit 1); name the concept
by path.

## 9. Core commands

The core commands are `init`, `lint`, `mv`, `status`,
`new`, `skill`, `block-ids`, `rules` and `updates`. Any other first argument is dispatched to a plugin (§2.2).

### 9.1 `loci init`

Run in the vault root. If the directory is not inside a git work tree, `init` first
runs `git init`. If it is inside one but not at its root, it refuses
(`vault.not-git`). It creates:

- `loci.toml` with every key of §11 written out;
- `RULES.md` (`# Rules` and an empty `## Lessons` section) and `STYLE.md`
  (`# Style`);
- the `.gitignore` line `/.loci/`;
- `AGENTS.md`, the committed stub (compiled into the binary):

  ```markdown
  # Agents

  This vault is managed by loci (https://github.com/yuxqiu/loci).

  1. Check that the `loci` command is installed; if not, install it as described at
     the URL above.
  2. At the start of a session, read the framework rules (`loci rules`), then
     `RULES.md` (this vault's rules and lessons) and `STYLE.md` (the user's writing
     style), which override the framework rules where they differ.
  3. Before each task, run `loci status` and act on what it reports.
  ```

Refuses (`init.exists`) if `loci.toml` exists. Lines are appended to `.gitignore`
only if missing; any other existing file is left untouched and listed as skipped.
A symlinked `RULES.md`, `STYLE.md`, `AGENTS.md` or `.gitignore` is refused before
anything is written (`file.symlink`, §3).
`init` writes nothing plugin-specific and never commits. `data`: `{"created":
[paths], "skipped": [paths]}`.

### 9.2 `loci lint`

Lints the working tree with the core rules, then runs every installed plugin's lint
hook and merges its diagnostics (§2.3). Exit 1 iff an error is reported. `data`:
`{"files", "errors", "warnings", "plugins": [names]}`; `errors` and `warnings` count
the merged diagnostics.

`loci lint --fix [--unsafe-fixes] [--only <code>] [--dry-run]` applies the core
diagnostics' fixes (§8): safe ones, unsafe ones too with `--unsafe-fixes`, never
display-only ones; `--only` keeps those of one code. Fixes are applied in memory, in
passes: each pass applies every allowed fix that neither overlaps nor touches
another; passes repeat on the re-linted result until no fix applies, at most ten.
Then the result is checked: no error code may have more diagnostics than before, and
every link that resolved must still reach the same file. A fix whose edits fall
outside its note is a loci bug (`lint.fix`, exit 3).
A failed check is `lint.fix-verify` (exit 1) and nothing is written; otherwise the
change is written as `mv` writes and the vault is linted again. `data` adds
`"fixed": [{"code", "path", "message"}]` and `"dry_run"`. `--dry-run` writes nothing
and reports the fixes, the files they would touch and the core index rules'
diagnostics after them. `--only` takes a code in a rule's row of `lint::RULES` or
`update.<id>` for a known update; any other is `lint.unknown-code`. A vault update's
How applies it with `--only update.<id>` (updates spec §2).

As `cargo fix`, `--fix` refuses a working tree with uncommitted changes
(`lint.dirty`), so the diff is exactly the fixes, unless `--allow-dirty` is given or
it is a `--dry-run` (D195).

### 9.5 `loci mv <from> <to> [--dry-run]`

`--dry-run` plans and checks the move as usual, then reports it (`data.dry_run`: true,
and in the human form each rename and edit) and writes nothing.

Arguments are vault paths. `<from>` is a markdown file, another file, or a directory
(moved recursively). A file or folder stored under a non-NFC name (`path.not-nfc`) is
named by its NFC form, so that `mv` can fix it; an exact name wins. A folder moves
whole: if it holds a file loci does not move (a submodule), the move is refused
(`mv.from`). A source can be renamed within the layout, keeping its
extension; a move that would make it stop being a source (out of `sources/`, or out
of the layout) or change its extension is refused (`mv.source-file`), and so is a moved concept that
would stop being a concept (`mv.no-area`). Then every destination follows the path
rules lint checks (`sources.layout`, `kind.unknown`,
`slug.format`, `journal.path`; §3, §6.2, §6.4, §6.6) and is refused with that
rule's code, before the case and existence checks.
A file under `sources/` that is not a source (`sources.layout`) may be moved out. A
source that differs from its committed version cannot be moved, since the rename
would hide the change from `sources.changed` (`mv.source-changed`). A path core never reads (§3: `plugins/`,
`.git/`, `loci.toml`, the root `.gitignore`) is refused as a source (`mv.from`) or a
destination (`mv.to`).

Refuses (exit 1, no writes) if: `<to>`, or any moved file's destination, exists on
disk, including files lint does not read (`mv.exists`); `<to>`, or a folder on its
path, differs from an existing name only in letter case (`path.case-twin`, as for
`new`: on a case-insensitive file system, or with git's `core.ignorecase`, it is the
existing file or folder and links would dangle; elsewhere it makes twin folders. The
message says to rename with `git mv -f` when the existing name is `<from>` itself, to
move the whole folder when it is `<from>`'s own folder, and otherwise to use the
existing spelling or another name; a destination that breaks a path rule is refused
for that first, so the advice never leads to a name lint rejects); `<from>` is missing
or ignored (`mv.from`); `<to>`, or any moved file's destination, is ignored by git
(`path.ignored`, as for `new`: a moved file must stay in the vault); a note would lose
its `.md` extension, or a file that is not a note would gain one (`mv.to`); `<from>` names two stored spellings of one NFC name (`mv.from`); a file that ends as a concept
gets a slug that equals another concept's slug (`mv.collision`); a destination
breaks a path rule (its lint code, above); a moved concept would end outside an area
(`mv.no-area`, saying when the destination would be an area's `AREA.md`); a source
would stop being a source or change its extension
(`mv.source-file`); a moved source differs from HEAD
(`mv.source-changed`); the post-move check in step 3 fails (`mv.verify`).

Steps:

1. Compute the path map (old → new) for every moved file.
2. In every file outside `sources/` and `plugins/` (which are not parsed for links),
   find wikilinks and frontmatter links whose resolved target is in the map and
   compute an edit of the target bytes only (fragment, label, size and text kept):
   - a concept linked by bare slug stays bare, with the new slug;
   - otherwise the new root path, without `.md` for notes, with the extension for
     other files;
   - `prereqs` values are edited inside their quotes, through their spans (§4.4).

   Markdown links are never edited.
3. Build the post-move tree in memory, re-resolve every link outside `sources/` and
   `plugins/`, and check that each previously resolving
   one resolves to the mapped image of its old target. On any failure write nothing.
4. Write: rename with the filesystem (not `git mv`), and write edited files via temp
   file + rename.

A rename edits links only, never the renamed note: its old slug is not kept.

`data`: `{"moved": [[from, to]], "edited": [{"path", "edits"}]}`.

### 9.6 `loci status`

Reports the state that changes from task to task, each part even if an earlier one
fails. It writes nothing and does not run lint.

1. **Entry point.** A missing `AGENTS.md` is `install.missing` (warning). Skills
   are not checked: where they are installed is the user's choice (§12), and
   `loci skill show` prints them.
2. **Uncommitted changes:** counts of modified, deleted, added and untracked paths,
   as `git status` reports them. A path whose name is not UTF-8 is not counted
   (where core reads files, such a name refuses the vault, §3).
3. **Agent work to review:** the number of tasks recorded by `loci done`
   (m1-m4 §6).
4. **Inbox:** `N file(s), M uncommitted (drafts 4, sources 7, …)`, counting the
   files under `inbox/` by their folder under `inbox/` (a file directly in `inbox/`
   is counted as "directly in inbox/"); then up to 10 uncommitted inbox files
   (untracked or differing from `HEAD`) by name, then `- and K more` if there are
   more. Uncommitted inbox files give one warning, `inbox.uncommitted`, with no
   path: "<M> inbox file(s) uncommitted: commit them before processing; a dissolved
   draft must be in git". A last line names the next step: `Next: ask the user to
   commit these before processing the inbox.` when some are uncommitted, `Next:
   process them with the intake skill (`loci skill show intake`).` when the inbox
   holds only committed files.
5. **Updates:** when vault updates are waiting (§9.11), `N waiting (<ids>); read
   them with `loci updates``. A vault ahead of this loci is warning
   `updates.newer`.

A failing part is a warning and its `data` is `null`: `git status` failing is
`status.git` (`changes` and `inbox.uncommitted` are `null`), and so is listing the
agent records failing (`agent_records` is `null`). Like every command, `status`
reads the vault's files from its file list (§3), so a git failure while listing
the vault refuses it. The framework rules, `RULES.md` and `STYLE.md` are not
printed; the agent reads them at the start of a session (§9.1).

Exit 0 unless the command cannot run. `data`: `{"changes": {"modified", "deleted",
"added", "untracked"} or null, "agent_records": n or null, "inbox": {"files": n,
"by_folder": {folder: n}, "uncommitted": [paths] or null}, "updates": [waiting
ids]}`; in `by_folder`, files directly in `inbox/` are counted under `""`.

### 9.7 `loci new <path> [--title <title>]`

`<path>` is `concepts/<area>/<slug>.md`, or deeper in sub-folders of the area at any
depth (`.md` may be omitted). Refuses
(exit 1, no writes) if anything exists at the path (`new.exists`), the slug fails §6.2
(`slug.format`), the slug equals another concept's slug (`new.collision`), the path
is not inside an area or is an area's `AREA.md` (`new.no-area`, worded as for `mv`),
or it fails the destination checks `mv` makes
(§9.5): it differs from an existing name only in letter case (`path.case-twin`) or is
ignored by git (`path.ignored`). Otherwise it
allocates a ULID and writes:

```markdown
---
id: 01JB9XQ7Z3K4M5N6P7Q8R9S0TV
prereqs: []
---
# <title, default: the slug>
```

The skeleton lints clean. `new` then runs `git add -N` on the file, as the framework
rules ask of every file an agent creates; if that fails the file stays and the
warning `new.git-add` says to run it by hand. `new.collision` names the note that
has the slug. `data`: `{"path", "id"}`.

### 9.8 `loci skill show [<name>]`

Prints the core skills, compiled into the binary, together with the skills of every
installed plugin (from `loci-<name> skills --json`, §2.3). It writes nothing.

- No name: list all skills, one per line as `<name>: <description>`, where the
  description is the `description:` field of the skill's frontmatter. `data`:
  `{"skills": [{"name", "description", "plugin": <name or null>}]}`.
- With a name: print that skill's `SKILL.md` verbatim. An unknown name is
  `skill.unknown` (exit 1) and lists the valid names. `data`:
  `{"name", "description", "body", "plugin": <name or null>}`.

A plugin whose `skills` command fails is `plugin.failed` (§2.3, an error, so the
command exits 1) and its skills are omitted; the other skills are still listed.

### 9.9 `loci block-ids <note> --section <heading>`

Assigns block ids to top-level blocks that have none, in one section. `<note>` is a
readable note of a managed kind, given as a note argument (§8). A note that is not
found or is not of a managed kind is refused (`block-ids.kind`, exit 1). `--section` is required.

- **Scope:** the paragraphs and top-level list items directly under the H2 whose
  heading text (§4.6) equals `<heading>`, up to the next H1 or H2. No such H2 is
  `block-ids.no-section` (exit 1). If several H2s have that text, every one of them
  is processed. Nested list items and paragraphs inside list items are never targets;
  they carry ids only if written by hand. An item that starts with a nested block (a
  quote, a fence) has no leading text and is not a target. Headings, code blocks, tables and HTML are
  never targets.
- **Id:** a ULID (ulid/spec), from one `ulid::Generator` per run, used as is.
- **Edit:** ` ^<id>` is appended, by splicing (§4.5), to the end of the last
  non-blank line of the target's id slice (§4.6), before its line ending: the
  leading text for a list item (so before any nested list), the paragraph for a
  paragraph.

It never changes an existing id or any other byte, and a second run changes nothing.
`data`: `{"path", "section", "assigned": [{"line", "id"}]}`.

### 9.10 `loci rules`

Prints the framework rules compiled into the binary
(`include_str!("../share/loci/rules.md")`). It needs no vault and writes nothing.
`data`: `{"rules": "<text>"}`.

### 9.11 `loci updates [--all] [--handled <id>]`

Vault updates: changes a loci release asks of a vault (a new `AGENTS.md` stub, a
removed field), offered by the agent and applied only on the user's yes. The design
and its reasons are in `docs/specs/updates.md`; this section is the contract.

- **The list** is compiled into the binary (`share/loci/updates.md`), append-only:
  each entry is `## u<NNNN> · <YYYY-MM-DD> · <title>` with **Offer** (what changes,
  for the user), **How** (what the agent does on a yes) and **Done when** (criteria
  the agent verifies and reports). Ids only increase by one, and no entry is ever
  edited or deleted (a unit test checks the ids and fields); the binary ships all.
- **State** is the `updates` key of `loci.toml` (§11): the last update handled,
  applied or declined. No key means none handled. `loci init` writes the newest id.
- **No flags:** prints the procedure the agent follows, then every waiting update
  (those after the key) in full; `No updates waiting.` when there are none. `data`:
  `{"waiting": [{"id", "title", "text"}]}`. Writes nothing.
- **`--all`:** prints every update this loci knows. `data`: `{"updates": [...]}`.
- **`--handled <id>`:** sets the key to `<id>`, in place in `loci.toml`, recording
  every update through it as handled. An id this loci does not know is
  `updates.unknown`; one already handled is `updates.order`. The edited file is
  parsed before it is written; if it does not parse, nothing is written
  (`updates.write`, exit 3: a loci bug). `data`: `{"handled"}`.
- A key newer than every update this loci knows is `updates.newer` (exit 1).

## 11. `loci.toml`

```toml
schema = 1
updates = "u0003"   # the last vault update handled (loci updates)

[budgets]           # characters (Unicode scalar values)
area_paragraph = 600
note = 12000        # body characters after the frontmatter (size.note)
```

- `updates` is the last vault update handled (§9.11), `u` and four digits; it may be
  omitted (none handled). `loci updates --handled` sets it.
- Every key under `[budgets]` has the default shown and may be omitted.
- Unknown keys, wrong types and an unknown `schema` are `config.invalid`. There are
  no plugin sections; a plugin keeps its configuration under `plugins/<name>/`.
- **Schema changes.** `schema` changes only when a vault written for the old
  version cannot be opened by the new one: a changed `loci.toml` format, or a change
  to what `Vault::open` reads. Every other format change (a removed or renamed field,
  file or folder, a new requirement) is a vault update (updates spec), marked in
  lint's edition tables (§7.3) when lint can find the old form. A loci reads exactly one schema
  and refuses any other with a message naming the supported one.
- **Upgrades.** A schema change ships with `loci upgrade`, which refuses a dirty
  working tree, edits the working tree only (never commits), converts one schema
  step at a time, is safe to run twice, and never changes note prose. None is
  planned; it is built with the first schema change.

## 12. Package

The Nix flake builds the workspace and provides one package per binary: `loci` and
`loci-learn`. Each installs its binary and its skills under `share/loci/skills/`
(`<name>/SKILL.md`, for core and plugins alike). The framework rules (`share/loci/rules.md` in the source
tree), the `AGENTS.md` stub and the core skills are compiled into `loci`; a plugin's
skills are compiled into the plugin. No rules file is installed into the vault.

loci does not install skills into vaults or agent configurations. Users install
the `share/loci/skills/` folders wherever their agent loads skills from; any agent
can also read them with `loci skill show`.

The Nix package builds offline from `Cargo.lock` with no extra inputs. It installs
`LICENSE` under `share/doc/<package>/`.

### 13.3 Properties (proptest)

Over generated vaults of concepts, areas, views and journal entries with random
slug and root-path wikilinks (including CJK names and table pipes): `mv` of any file
or directory keeps every resolving link outside `sources/` resolving to the mapped
target; `lint` output is byte-identical across runs;
splicing an empty edit list is the identity, and one-pass splicing equals applying
edits one at a time from the end.

Scale (on demand): a generated vault of 10k–100k notes; record `lint` and `status`
wall time.
